# Running Unify SDLC on a server

`compose.yml` is the Archon server the pack runs on: Archon's dev build at a pinned commit, plus the toolchain the projects' checks need (uv, Node, pnpm, gitleaks), a throwaway PostgreSQL for tests, a merge guard for agent shells (`gh`, `git`), and a timer loop (Archon has no timer on Linux).

## Set up

1. Deploy `compose.yml` (Dokploy compose or plain `docker compose`) with the secrets named at its top. Keep the console on a private network.
2. In the container, as `appuser`: `archon plugin add redikultsev/agentic-sdlc-atlas/implementations/archon@<unify-sdlc tag>`.
3. Register the project (`archon` console or CLI), clone it, and add to its default branch: `.pipeline/project.yaml`, `.pipeline/trusted.json`, `.archon/packs/redikultsev.unify-sdlc.yaml`, model aliases in `.archon/config.yaml`. The trial repository's versions are a working example (see `../SPEC.md`, "Settings and setup per project").
4. `archon trigger whoami`, then `archon pack bindings redikultsev.unify-sdlc --repo github.com/<owner>/<repo> --host archon-server --run-as <id> --cwd <checkout> --out /.archon/bindings`. The timer loop fires the files with a schedule; the server (`ARCHON_TRIGGER_HOST=archon-server`) starts the chained stages.
5. Users and roles (decision 64): turn web auth on (with it off, an unidentified console is the operator and may answer any gate). The Operator is an Archon user with the admin role, and the `--run-as` identity of step 4 is the Operator's. Every other user is a member: Archon keeps users from before roles as admins, so demote them with `archon user role <id> member`. The read server's HTTP identity (`../read-server/`) is a member too.
6. The Supervisor (decision 65; `../supervisor/README.md`): Archon's own chat, where the Operator writes as themselves, so Archon does not refuse its answers; its instructions and its folder's deny rules hold it back. Make a folder outside `~/.archon/workspaces` and every checkout, copy the three files and the config block of `../supervisor/README.md` into it under their installed names, fill in the console's address and the pack's path, register it with `/register-project --folder "supervisor" <path>`, and chat in that project on the Claude provider. For it to file requests (decision 66; `../request-server/README.md`), add to the server's secrets, never to a file: `REQUEST_GITHUB_TOKEN`, a fine-grained token of an account of its own (not the Operator's, not `pipeline_login`, on no project's `.pipeline/trusted.json`) with access to the pipeline's repositories only and one permission, Issues: read and write; give that account the triage role on each repository. And `REQUEST_PROJECTS`, the projects it may file in with each one's `intake_label` as in the project's pack settings, a project with `.pipeline/tracker.yaml` marked `"tracker": "map"` (refused): `{"<owner>/<repo>": {"intake_label": "<label>"}}`; optionally `REQUEST_DAILY_CAP` (default 10). Every agent session on the server inherits these, like the pack's own forge credential. Without them the Supervisor drafts requests for the Operator to file.
7. `archon workflow run redikultsev/unify-sdlc:unify-ping --input repo_host=github.com --input repo_path=<owner>/<repo>` and fix what it reports.
8. Label an issue with the pack setting `intake_label` (or start one by hand: `archon workflow run redikultsev/unify-sdlc:unify-triage --input number=<n> --item issue-<n>`). Gates appear in the console's attention list.

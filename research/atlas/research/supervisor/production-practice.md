# Supervisor authority: what production practice and incidents say

Access date for every link: 2026-11-24. Marks: **V** verified in a primary source read in full or in the relevant part; **S** secondary (press, blog, search summary, primary not reached); **I** inferred by the author.

## Question

The Supervisor is a long-lived chat agent that is the Operator's single interface to the pipeline: report status, create work items, answer gates (accept, approve a spec, merge, release), cancel, pause. Should it be forbidden anything, need confirmation for some actions, or be allowed everything the Operator can do? This note covers only production practice, incidents and security guidance. Repository context: decisions 21 (sandbox, no merge rights for agents), 25 (R0 merge only by a rules file; the agent's R0 is a forecast), 38 (every option carries the exact action code takes), 39 (request text is data; trust read by code), 46 and 47 (project map; production deploy rights only in the deploy-recipe step; own service account) in `docs/decisions.md`.

## Short answer

1. No surveyed vendor lets an agent hold the same authority as the human it serves without a mechanism between them. The mechanisms differ: capability not granted (GitHub, Stripe, Spotify), sandbox plus approval-on-escape (Codex, Claude Code), classifier in front of actions (Claude Code auto mode), policy as code (OpenAI harness linters, Google runtime policy), or reversibility and cheap correction (OpenAI repository, Replit's backups).
2. The consistent "always human" class is: approving or merging the agent's own work where independence matters (GitHub: requester and Copilot cannot approve), production changes on critical resources (Amazon after its incident), and anything that leaves the sandbox or the trust boundary.
3. Where agents act alone, the grant is narrow and mechanical (R0-like): the agent never decides its own tier. OpenAI is the one first-party exception that lets agents merge their own PRs, and says it depends on repository tooling and a high-throughput, cheap-correction setting.
4. Prompts to a human do not work as the only control: Anthropic reports users accept 93% of manual prompts. Confirmation must be rare, specific and tied to irreversibility, or it decays into rubber-stamping.
5. Incidents with broad authority (Replit, Kiro, Amazon Q extension, MCP and CI injection attacks) share three causes: the agent held production or secret-bearing authority in the same session that read untrusted text; an instruction ("code freeze") lived only in the prompt; and the check that failed was a model's judgement, not code.
6. Guidance (OWASP, Meta Rule of Two, lethal trifecta, CaMeL) says the dangerous object is not "an agent with many rights" but "one session combining untrusted input, sensitive access and outward action". A Supervisor that reads work-item text and answers gates is that combination unless gates are separated.
7. Strongest honest position: the Operator's rights are not the right unit. Grant the Supervisor the Operator's intents, not the Operator's credentials; keep a short list that code, not the Supervisor, refuses.

## Practice per company

**Anthropic (Claude Code).** Default is read-only; edits and commands need approval; stated principle: ask before actions that modify code or systems, and humans keep control before high-stakes decisions (V: [framework post, 2025-08-04](https://www.anthropic.com/news/our-framework-for-developing-safe-and-trustworthy-agents)). Modes: manual, accept-edits, plan, auto, don't-ask, bypass; bypass is for isolated containers only, offers no prompt-injection protection, cannot be entered mid-session, and admins can disable it; repository state and agent config (`.git`, `.claude`, `.mcp.json`) are protected paths, prompted or sent to the classifier even where edits are allowed (V: [permission modes](https://code.claude.com/docs/en/permission-modes)). Sandboxing cut permission prompts by 84% internally; needs both filesystem and network isolation (V: [sandboxing post](https://www.anthropic.com/engineering/claude-code-sandboxing)). Auto mode replaces prompts with a classifier: tier 1 read-only tools, tier 2 in-project edits, plus more than twenty block rules in four groups (destroy or exfiltrate data, degrade security posture, cross trust boundaries, bypass review or affect others). Measured: 0.4% false positives on real traffic; 17% false negatives on real overeager actions (n=52); 5.7% on synthetic exfiltration; users accepted 93% of manual prompts (V: [auto mode post](https://www.anthropic.com/engineering/claude-code-auto-mode)). Multi-agent research: effort-scaling rules were added because early versions spawned 50 subagents for simple queries; multi-agent uses about 15x chat tokens (V: [multi-agent post](https://www.anthropic.com/engineering/built-multi-agent-research-system)).

**OpenAI.** Codex: sandbox modes read-only, workspace-write, danger-full-access; approval policies on-request, never, granular; network off by default; `.git`, `.codex`, `.aws` read-only inside writable roots; optional auto-review agent for approval requests that fails closed and denies critical-risk actions (V: [approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)). Internal "harness engineering": agents open, review and often squash-merge their own PRs; humans "may review, but aren't required to"; constraints are custom linters and structural tests with remediation text; minimal blocking merge gates justified by "corrections are cheap, and waiting is expensive", with the caveat that it would be irresponsible at lower throughput and depends on tooling investment (V: [harness engineering](https://openai.com/index/harness-engineering/)).

**Stripe (Minions).** Fully unattended runs from a Slack message to a PR; devboxes isolated from production and the internet "so no human permission checks are needed"; curated tool subsets from a central MCP server (400+ tools); at most two CI rounds; engineers review every PR before merge (V: [Stripe Dev blog](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents)).

**Spotify (Honk, Fleet Management).** Agent runs in a container with few binaries; pushing, Slack interaction and prompt authoring are done by surrounding infrastructure, not the agent; failing verifiers prevent PR creation; an LLM judge vetoes about a quarter of PRs, mostly for going beyond the prompt (V: [part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). Review and merge stayed in the existing Fleet Management infrastructure; most of 2.5 million automated PRs merged automatically after safety checks (S: [InfoQ 2026-10](https://infoq.com/news/2026/10/spotify-ai-quality-controls), [part 1](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1) V for the unchanged-infrastructure claim).

**Ramp (Inspect).** Per-session VM; clone via app installation token, PR opened with the prompting user's token and commits in the user's name; the post recommends this so a user cannot approve their own change through the app identity (V: [Ramp builders](https://builders.ramp.com/post/why-we-built-our-background-agent)). Merge rights not described.

**Google.** Secure-agents approach: clearly defined human controllers, carefully limited powers, observable actions, hybrid of deterministic controls and reasoning-based defences (V abstract: [Google Research](https://research.google/pubs/an-introduction-to-googles-approach-for-secure-ai-agents/)). CaMeL (Google DeepMind and ETH authors): control flow extracted from the trusted query, capabilities on data, policy enforced at tool calls; 77% of AgentDojo tasks with provable security versus 84% undefended (V: [arXiv 2503.18813](https://arxiv.org/abs/2503.18813)).

**GitHub (Copilot coding agent).** Pushes only to one `copilot/` branch; cannot approve or merge its own PR; the requester cannot approve it; Actions workflows do not run on its changes until a person with write access approves; internet firewall; hidden characters filtered from issue and PR text; session read-only without write access (V: [risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations), [about](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)).

**Microsoft (Magentic-UI, research prototype).** Action guards: asks permission before consequential or irreversible actions; optional ask-before-every-action; co-planning before execution; human feedback raised GAIA completion from 30.3% to 51.9% in a simulated-user test (V: [Microsoft Research](https://www.microsoft.com/en-us/research/blog/magentic-ui-an-experimental-human-centered-web-agent/)).

**Amazon.** After the December 2025 Kiro incident (below) Amazon stated it added mandatory peer review for production access; Kiro asks for authorization by default, the engineer's role was broader than expected (V for Amazon's quoted statement via [The Register](https://www.theregister.com/2026/02/20/amazon_denies_kiro_agentic_ai_behind_outage/); the underlying FT account is S).

**Cognition (Devin).** Docs: standard branch protection applies to Devin; human engineers review and approve PRs; Devin keeps org-level permissions rather than mirroring the session user's (V/S mix: [SDLC integration](https://docs.devin.ai/enterprise/sdlc-integration), [GitHub integration](https://docs.devin.ai/integrations/gh)). Whether Devin's identity can satisfy a required review is not stated (unverified).

**Not covered by a first-party source in this pass:** Cloudflare, Shopify, Meta engineering (other than the Rule of Two), AI-DLC details.

## Action classes: who allows an agent to act alone, who requires a human

| Action class | Alone | Human required | Mechanism |
|---|---|---|---|
| Read status, logs, code | All surveyed (Claude Code read-only default, Codex read-only, Copilot read-only without write access) V | none | read-only tier; allowlist of read tools |
| Create work (issue, branch, PR, task) | Copilot (one branch, one PR per task), Stripe, Spotify, Ramp V | none to create; review before merge | scoped branch; PR opened by infrastructure or user's token |
| Approve a spec or plan | Not found as an agent-alone action anywhere | Magentic-UI co-planning; Claude Code plan mode needs plan approval V | plan gate before edits |
| Merge | OpenAI repository (agents squash-merge own PRs) V; Spotify automerge after safety checks S; Claude Code pushes to the working branch inside a classifier exception V | GitHub (never the agent, never the requester) V; Stripe (every PR) V; Devin docs V | rulesets and branch protection; mechanical rules per change type; separate identity for author and approver |
| Deploy or release | Not found for production in first-party material except OpenAI's low-gate culture (V, caveated) | Copilot workflows wait for a write-access human V; Amazon production changes need peer review after incident V | workflow approval; separate credentials; peer review |
| Roll back | No first-party statement found | Replit offered one-click restore after the fact V (CEO quoted in The Register) | reversibility, backups; cheap correction (OpenAI) |
| Change the pipeline's or agent's own rules and config | None | Claude Code: protected paths (`.claude`, `.mcp.json`, `.git`) prompted or classifier-gated V; Codex: `.codex`, `.agents` read-only V; bypass mode refused for admins V | path protection; managed settings that disable modes |
| Spend and runaway work | Stripe: two CI rounds V; Anthropic: effort-scaling rules V; Codex: network off by default V | exceeding sandbox or network: ask V | numeric limits in code; network closed by default |
| Act outside the trust boundary (network, secrets, external send) | None by default | Codex on-request V; Claude Code auto mode blocks "cross trust boundaries" V | network isolation; block rules; allowlists |

## Guidance and what it implies

- **OWASP LLM06:2025 Excessive Agency.** Three root causes: excessive functionality, permissions, autonomy. Prevention: minimise tools; avoid open-ended tools such as raw shell; act in the user's context with minimum scope; require human approval for high-impact actions; **complete mediation** (authorise in the downstream system, not by asking the LLM); log and rate-limit (V: [OWASP](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)).
- **OWASP Top 10 for Agentic Applications 2026** (published 2025-12-09): introduces **least agency**; ASI01 goal hijack, ASI02 tool misuse, ASI03 identity and privilege abuse; ASI04 to ASI10 not read (S: [search summary](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/); primary page not read).
- **Lethal trifecta** (Willison, 2025-06-16): private data, untrusted content, external communication; only reliable defence is not combining all three; guardrail products do not reliably stop attacks (V: [post](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)).
- **Meta Agents Rule of Two** (2025-10-31): within one session an agent should have at most two of: processes untrusted input, accesses sensitive systems or private data, changes state or communicates externally; a supplement, not a replacement, for least privilege (S: [search summaries](https://ai.meta.com/blog/practical-ai-agent-security/); the primary host was unreachable from this environment, so wording is unverified). Willison says it adds "changing state" to his trifecta (V on that remark: [his post](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)).
- **CaMeL** (above): enforce policy on data flows at tool-call time; cost is utility (77% versus 84%) (V).
- **NIST/CAISI.** RFI on securing AI agent systems (Federal Register 2026-01-08, docket NIST-2025-0035) and an AI Agent Standards Initiative (2026-02); outputs voluntary; no agent-authority rule found (S: [NIST news](https://www.nist.gov/news-events/news/2026/01/caisi-issues-request-information-about-securing-ai-agent-systems)). CISA: nothing found.

Implication for a Supervisor that reads untrusted work-item text and can answer gates (I): it has the untrusted-input leg (request text, comments, agent reports) and the state-changing leg (accept, approve, merge, release, cancel). Whether it has the sensitive-data leg depends on what its tools return (credentials, private repositories, other projects). Under the Rule of Two the safe configurations are: (a) it never reads untrusted text raw (it reads the engine's copy of approved text and structured summaries, as decisions 39 and 47 already do for agents), or (b) it reads untrusted text but a human, not the Supervisor, supplies the state-changing decision. A Supervisor that does both with no separation is the pattern behind the GitHub MCP and Comment-and-Control incidents.

## Strongest case for "forbid nothing"

Stated fairly: (1) The Supervisor is the Operator's interface, not an extra actor; every limit moves work back to the Operator, whose attention is the scarcest resource (decision 1). (2) Prompts and confirmations fail in practice: 93% acceptance (V), 84% of prompts removable by sandboxing instead (V); a confirmation on every gate answer reproduces approval fatigue. (3) The only first-party shop that removed gates (OpenAI) argues that cheap correction beats prevention when throughput is high (V). (4) Prohibitions written as prompt text are the weakest control; Replit's freeze was one (S). (5) A Supervisor forbidden something just gets the Operator to do it by hand through the same chat, so the prohibition protects nothing against the Operator and only slows legitimate use. (6) Everything it does is logged and attributable, and the engine, not the Supervisor, performs the action (decision 38), so a mistaken answer is bounded to a gate choice.

## Strongest case against

(1) Authority is not the Operator's alone: the Supervisor acts on text the Operator did not write (work items, agent reports), so "what the Operator may do" is the wrong bound; the right one is "what the Operator would choose having read this text". (2) Every incident above involved an agent holding a right in the same session that consumed untrusted or misleading input, and the check that failed was model judgement (Claude Code's classifier misses 17% of real overeager actions, V). (3) Irreversible actions (production release with data migration, deleting work, closing with data loss) do not benefit from "cheap correction"; OpenAI's own caveat limits its approach to high-throughput, cheap-fix settings (V). (4) Independence is a control in itself: GitHub, Ramp and Amazon separate author from approver precisely because one identity doing both removes the check (V); a Supervisor that both creates work and approves it collapses that. (5) Pipeline-rule changes by the Supervisor are privilege escalation: it would be changing the limits that bind it, which every surveyed vendor protects by path or managed setting (V). (6) A hijacked session with unlimited gates can approve an attacker's spec, merge, and release in one conversation; with no code-level limit nothing stops it.

## What this means for our Supervisor (I)

- Frame the rule as "no capability the Operator lacks, and not every capability the Operator has": give the Supervisor the Operator's intents routed through the Orchestrator, never the Operator's credentials. The Orchestrator already performs the action; keep it so (decision 38).
- Forbid by code, not by prompt, a short list: changing the pipeline's own rules, trusted-author lists, project map and risk rules (R2 paths, decisions 25, 46); creating or widening its own permissions; holding production deploy credentials (decision 47 already denies this to agents).
- Never let the Supervisor answer a gate on text that it, rather than code, has read raw from an unapproved author; feed it only the engine's approved copy and structured fields (decisions 39, 45, 47).
- Keep author and approver apart where it matters: a work item the Supervisor created at the Operator's word is fine; a spec or merge it created and then approves on its own judgement is not. The Operator's explicit message is the approval, bound to the exact item and revision.
- Confirm only irreversible or wide actions: release to production, merge of R2, cancel of work with unpushed output, bulk operations, and any action touching more than one item; everything else executes with an undo path and a log line. Keep confirmations rare so they stay meaningful (93% finding).
- Do not let the Supervisor change R-tier or size on its own; the Operator's correction is an input, the agent's R0 stays a forecast (decision 25).
- Put numeric limits in the Orchestrator: actions per hour, items per command, gate answers per session; the multi-agent spawning incident was fixed only with a prompt rule, which is weaker.
- Record every Supervisor action with who asked (the Operator's message id), so reversal and audit are possible; measure how often confirmations are accepted unchanged, as decision 38 does for recommendations.
- Treat injected text reaching the Supervisor via status queries (a work item titled with instructions) as the main threat; strip hidden characters (GitHub does) and display item text as quoted data.
- Revisit "forbid nothing" only after a period of logged use: remove a confirmation when its accept rate is near 100% and the action is reversible (the kill-switch logic of decision 25 applied to the Supervisor).

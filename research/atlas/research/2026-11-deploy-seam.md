# A deploy seam for more than one deploy shape

Research of 2026-11-24. Primary sources only: vendor and project documentation, specifications, and the source of the two engines (Archon `dev` at `bd34eec`, cezar `main` at `7db6462`, shallow clones of 2026-11-24). All pages accessed 2026-11-24 unless stated. **V** = read in the source on that date; **I** = inferred by this note from verified facts. Builds on [2026-11-deploy-and-watch.md](2026-11-deploy-and-watch.md) (rollout, automatic rollback, watching) and [2026-11-merge.md](2026-11-merge.md) (merge queues, stale approvals); their findings are not repeated.

## Question

The model's stage 8 has one shape (decisions 8, 24, 25, 26; `model/engine.c4` "8. Deploy & watch"; `implementations/archon/unify-deploy/`; `.pipeline/project.yaml` `deploy.hook` read in `.shared/policy.ts`): every merge deploys main to everyone, one Watcher per deploy, rollback by a revert PR. What is the smallest seam that also carries a second common shape: many service repos with `develop` and `master`; a CI server that builds an image from a git tag and runs "Deploy to Test" / "Deploy to Production" through its REST API (some services with helm); one shared test stand that must be checked for someone else's build; a PR tag deployed to that stand before merge and checked by a human tester; merge to `develop` only after the tester approves; a release tag to production; a smoke test after each deploy; rollback by redeploying the previous tag; a hotfix path when the stand runs something newer than production?

## Short answer

1. Every system read reduces to six concepts: **environment**, **version** (an immutable artifact reference), **promotion** (version → environment, leaving a deployment record), **gate** (human or automatic, bound to a version and an environment), **verification** (declared per environment, run after the deploy) and **rollback** (in every tool except a revert-based flow, rollback is a promotion of an older version). A seventh, **lock** (one deploy at a time per environment), is built into GitLab, GitHub, TeamCity and Kargo. (V, table below)
2. Our stage 8 hard-codes one value of each: environment = production, version = main after merge, promotion trigger = merge, gate = the Merge gate before merge, verification = the Watcher window, rollback = revert PR. Shape B is the same concepts with other values; it does not need another stage. (I)
3. A shared stand needs more than a lock. The lock in every tool only serialises deploy jobs; none checks whether the stand is still *in use* by a build someone is testing. "Occupied" has to be a seam fact: the version on the stand is not production's, and its holder is someone else. (V for the locks, I for occupancy)
4. Human QA approval is recorded in three ways: on the deploy job (GitLab, GitHub environments), on the version itself (Kargo `approvedFor`), or as a commit status on a SHA (GitHub statuses, "require deployments to succeed before merging"). Only the last two survive into a later step. In shape B the tester approves a pre-merge tag, but production receives a post-merge build: the approval must be carried over by content identity, or the release is unapproved. (V for the mechanisms, I for the risk)
5. Redeploying the previous version is the documented rollback of helm, Argo CD, Kargo, GitLab auto-rollback, TeamCity "Redeploy" and Dokploy. It is safe only while the schema stays compatible: expand–contract (already in decision 26) is the precondition for both shapes. (V, I)
6. A minimal deployer adapter needs four calls: `deploy(env, version)`, `wait(handle)`, `current(env)` (the version running now) and the list of past successful versions; rollback is `deploy(env, previous)`. TeamCity REST, helm, GitHub `workflow_dispatch` and Dokploy all provide them. (V per tool, I for the interface)
7. Neither Archon nor cezar models environments, deployments or rollbacks. Archon's forge API has no deployment or environment operation and its direction says it is "Not a deployment-infrastructure product"; cezar's only deploy is redeploying cezar itself. The seam has to live in our pack. (V)

## 1. Neutral vocabulary

- **CDEvents** continuous-deployment spec (event types end in `0.3.0`): subjects `environment` (`created`, `modified`, `deleted`; fields `id`, `source`, `name`, `url`) and `service` (`deployed`, `upgraded`, `rolledback`, `removed`, `published`; fields `id`, `source`, `environment`, `artifactId` as a Purl). `deployed`, `upgraded` and `rolledback` require `environment` and `artifactId`. `rolledback` = "an existing service instance … rolled back to a previous version". V: [github.com/cdevents/spec continuous-deployment.md](https://github.com/cdevents/spec/blob/main/continuous-deployment.md). There is no approval, lock or verification event in this spec (V, same page).
- **OpenGitOps** 1.0.0: desired state declarative, versioned and immutable, pulled automatically, continuously reconciled. V: [opengitops.dev](https://opengitops.dev/). Consequence: in GitOps a deploy is a change of the declared version, and rollback is declaring an older one (I).
- **GitLab**: environments with tiers (`deployment_tier`: production, staging, testing, development, other); each deploy job creates a deployment record in the environment's list; dynamic environments such as `review/$CI_COMMIT_REF_SLUG`; `auto_stop_in`. V: [docs.gitlab.com/ci/environments](https://docs.gitlab.com/ci/environments/). Protected environments block deploy jobs "until all required approvals are given"; the pipeline triggerer cannot approve by default; approvals and rejections are kept as history on the deployment; approval does not start the job. V: [deployment approvals](https://docs.gitlab.com/ci/environments/deployment_approvals/).
- **GitHub**: environments with protection rules (at most 6), required reviewers (up to 6, one approval suffices, optional "prevent self-review"), wait timer up to 30 days, deployment branches and tags matched against `GITHUB_REF`, custom protection rules by GitHub Apps (public preview), environment-only secrets released after approval. V: [deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Deployments API: a deployment has `ref` (branch, tag or SHA), `environment`, `transient_environment`, `production_environment`; statuses `error`, `failure`, `pending`, `in_progress`, `queued`, `success`, plus `inactive`. V: [REST deployments](https://docs.github.com/en/rest/deployments/deployments).
- **Kargo**: Warehouse watches repos and emits **Freight**, a "meta-artifact that references specific revisions of artifacts"; a **Stage** is a promotion target; stages link into a pipeline; **Promotion** moves freight into a stage's desired state, while Argo CD does the deploy. V: [core concepts](https://docs.kargo.io/user-guide/core-concepts/). A stage's `requestedFreight` names sources (`direct` from the warehouse, or upstream `stages`) with `availabilityStrategy` `OneOf`/`All` and `autoPromotionOptions`; auto-promotion is enabled per project. V: [working with stages](https://docs.kargo.io/user-guide/how-to-guides/working-with-stages). Steps are declared in `spec.promotionTemplate.steps` (`uses: git-clone`, `git-push`, …, or a `PromotionTask`). V: [promotion templates](https://docs.kargo.io/user-guide/reference-docs/promotion-templates).
- **Argo CD / Argo Rollouts**: an Application syncs declared state; `argocd app rollback [ID]` goes to a history ID or the previous version, and "Rollback cannot be performed against an application with automated sync enabled". V: [app rollback](https://argo-cd.readthedocs.io/en/stable/user-guide/commands/argocd_app_rollback/), [auto sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/). Rollouts verify with AnalysisTemplates (below).
- **Spinnaker**: pipelines of stages; Deploy (blue/green, highlander, custom), Manual Judgment (pauses until a user clicks Continue; may offer input choices that later stages read), Rollback Cluster, Canary Analysis (Kayenta; analysis only). V: [pipeline stages reference](https://spinnaker.io/docs/reference/pipeline/stages/).

| Concept | CDEvents | GitLab | GitHub | Kargo | Argo CD / Rollouts | Spinnaker |
|---|---|---|---|---|---|---|
| Environment | `environment` subject | Environment (+ tier; dynamic for review apps) | Environment | Stage | Application (target cluster/namespace) | Server group / cluster account |
| Version | `artifactId` (Purl) | Commit of the pipeline | Deployment `ref` / SHA | Freight | Git revision in sync history | Baked or found image |
| Promotion | `service.deployed` / `upgraded` | Deploy job with `environment:` | Job with `environment:`; Deployment object | Promotion (from promotionTemplate) | Sync | Deploy stage |
| Deployment record | the event itself | Deployments list per environment | Deployments + statuses | Freight `verifiedIn`, stage history | Sync history IDs | Execution history |
| Gate (human) | none | Protected environment approvals | Required reviewers | Manual approval → `approvedFor` | none in core (I) | Manual Judgment |
| Gate (automatic) | none | Rules, `needs` (I) | Custom protection rules, wait timer, branch/tag rules | Verified upstream, `requiredSoakTime` | Pre-promotion analysis | Check Preconditions |
| Verification | none | `action: verify` jobs (I: no built-in pass/fail object) | none built in | `spec.verification.analysisTemplates` | AnalysisTemplate / AnalysisRun | Canary Analysis |
| Lock | none | `resource_group` + process mode | `concurrency` group (separate from environment) | Promotions wait while verification runs | one sync at a time (I) | not read |
| Rollback | `service.rolledback` | Re-run older deployment; Auto Rollback | Re-run workflow on older ref (I) | Promote older Freight | `app rollback` | Rollback Cluster |

## 2. Pre-merge vs post-merge environments, and the shared stand

- **Per-PR environments**: GitLab review apps are "temporary testing environments that are created automatically for each branch or merge request", stopped by an `on_stop` job when the MR merges or the branch is deleted, or by `auto_stop_in`. V: [review apps](https://docs.gitlab.com/ci/review_apps/). GitHub: `transient_environment` marks an environment that "will no longer exist at some point"; `inactive` records it as destroyed. V: REST deployments (above).
- **Pre-merge deploy as a merge condition**: GitHub branch protection can "require that changes are successfully deployed to specific environments before a branch can be merged". V: [about protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). GitHub's own branch-deploy practice (deploy the PR branch, then merge) is in [2026-11-deploy-and-watch.md](2026-11-deploy-and-watch.md).
- **One slot, serialised**: GitLab `resource_group` lets one job hold the resource at a time; process modes `unordered` (default), `oldest_first`, `newest_first`, `newest_ready_first`. V: [resource groups](https://docs.gitlab.com/ci/resource_groups/). GitHub `concurrency`: "at most one running job or workflow in a concurrency group"; a new run replaces the pending one unless `queue: max` (up to 100 waiting, FIFO not guaranteed); "`concurrency` and `environment` are not connected". V: [control workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [control deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments). TeamCity deployment configurations: "you cannot simultaneously run two builds that belong to the one deployment configuration"; personal builds off; running an older build warns it "will override newer deliveries". V: [deployment build configuration](https://www.jetbrains.com/help/teamcity/deployment-build-configuration.html). Kargo: while verification is in progress "other Promotions to that Stage wait". V: [verification](https://docs.kargo.io/user-guide/how-to-guides/verification).
- **Not overwriting newer with older**: GitLab "Prevent outdated deployment jobs" fails an older deploy job that starts after a newer one ("The deployment job is older than the latest deployment"). V: [deployment safety](https://docs.gitlab.com/ci/environments/deployment_safety/).
- **Gap (I)**: all of the above stop two deploys from *running* at once or an old one from replacing a new one. None models "a person is still testing build X on the stand, do not replace it". On a single shared stand that is the failure that matters. The occupancy rule therefore has to be explicit: the stand is free when its running version equals production's, or when its holder is the requester; otherwise the requester waits, asks the holder, or takes the hotfix path. No source found that names this rule.

## 3. Human QA approval as a gate

| Where recorded | Bound to | Outlives the step? | Source (V) |
|---|---|---|---|
| GitLab deployment approval | One deployment job in one pipeline | No; approval does not even start the job | [deployment approvals](https://docs.gitlab.com/ci/environments/deployment_approvals/) |
| GitHub required reviewers | One job run; admins may bypass unless disabled | No | [deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) |
| Kargo `kargo approve --freight <f> --stage prod` | The Freight (version) for one Stage; shown as `status.approvedFor`; same rights as promoting | Yes; bypasses verification only | [working with freight](https://docs.kargo.io/user-guide/how-to-guides/working-with-freight) |
| Commit status `POST /statuses/{sha}` with a `context` | One SHA | Yes; can be a required check for merge | [commit statuses](https://docs.github.com/en/rest/commits/statuses), [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) |
| Spinnaker Manual Judgment | One pipeline execution | Input choices readable by later stages | [stages reference](https://spinnaker.io/docs/reference/pipeline/stages/) |

- Before or after merge: GitHub "require deployments to succeed before merging" and Kargo's per-version approval both allow the gate before merge; GitLab and GitHub environment approvals sit on a deploy job, usually after merge. Stale approval on GitHub is dismissed when "the pull request's diff changes". V: same pages.
- **Shape B risk (I)**: the tester approves image `tag-on-PR-branch`; production gets an image built from a later tag on the release branch. If anything else landed in between, production runs code no tester saw. Two ways to bind: (a) promote the *same* image digest that was tested (Kargo's model: freight is built once and moves); (b) record the approval on the tested git tree and require that the release build's tree, restricted to this service, equals it, or else re-test. The Google SRE book's release model relies on knowing "the exact contents of each release" via branch-and-cherry-pick. V: [sre.google release engineering](https://sre.google/sre-book/release-engineering/).

## 4. Rollback strategies

| Strategy | Who documents it | Safe when | Source (V) |
|---|---|---|---|
| Redeploy the previous artifact | helm (`helm rollback` default previous revision; `--history-max` default 10), Argo CD (`app rollback`, not with auto-sync), Kargo (promote older Freight; a manual promotion holds auto-promotion; Enterprise 1.11 restores the last verified Freight on failed verification), GitLab Auto Rollback ("redeploys the most recent successful deployment", off by default, at most every 3 min) and "run a new pipeline with a previous commit", TeamCity Redeploy, Dokploy `rollback.rollback` | Schema and data compatible with the older version; config not changed out of band | [helm rollback](https://helm.sh/docs/helm/helm_rollback/), Argo links above, [Akuity Kargo 1.11 post, 2026-07-27](https://akuity.io/blog/kargo-v1.11-auto-promotion-holds-freight-diffs-and-event-driven-promotions), [GitLab environments](https://docs.gitlab.com/ci/environments/), [deployment safety](https://docs.gitlab.com/ci/environments/deployment_safety/), [Dokploy rollback API](https://docs.dokploy.com/docs/api/reference-rollback) |
| Git revert, then a normal deploy | Our decision 26; trunk-based flows | One culprit PR is known; the revert is itself a new version that passes the pipeline | [2026-11-deploy-and-watch.md](2026-11-deploy-and-watch.md) |
| Feature flag off | Fowler: release toggles separate "release from deployment"; ops toggles / kill switches "disable or degrade that feature quickly" (2017-10-09) | The change was shipped dark behind the flag | [martinfowler.com feature toggles](https://martinfowler.com/articles/feature-toggles.html) |
| Roll forward with expand–contract | Parallel change: expand, migrate, contract (2014-05-13) | Always the precondition for the other three when a schema changes | [martinfowler.com parallel change](https://martinfowler.com/bliki/ParallelChange.html) |

- Google SRE Workbook: smaller artifacts make it "cheaper and easier to roll back any given release artifact"; with blue/green "rollback is a trivial reversal of the router change". The chapter does not discuss schema compatibility. V: [canarying releases](https://sre.google/workbook/canarying-releases/).
- DORA counts deployments that "require immediate intervention" (change fail rate, often ending in "a rollback or a hotfix") and "failed deployment recovery time" (replaced MTTR); "deployment rework rate" counts unplanned deployments caused by incidents. V: [dora.dev metrics guide](https://dora.dev/guides/dora-metrics/). Both shapes should record rollbacks and hotfixes as deployments with a reason so these can be computed (I).
- I: In shape A, a revert creates a new version and keeps the previous-version list linear; in shape B, redeploying an old tag leaves `master` ahead of production, so the next release tag must contain the fix or the revert, otherwise it re-ships the fault.

I: the common interface is `deploy(env, version) → handle`, `wait(handle) → ok | failed + log tail`, `current(env) → version` (read from the target, not from the CI server, so a manual change is visible), `history(env) → [version, at, ok]`. `rollback` needs no separate call: `deploy(env, history.lastVerifiedBefore(current))`. Dokploy's `rollbackId` is the one tool where rollback is a separate call; the adapter maps it. The present `deploy.hook` shell string covers `deploy` only; `wait` is the hook's exit code, and `current`/`history` do not exist, which is why rollback in decision 26 must go through a revert PR.

## 6. Verification after deploy

- Kargo: per Stage, `spec.verification.analysisTemplates` (plus `args`, `analysisRunMetadata`); runs after a successful Promotion; success marks the Freight `verifiedIn` that Stage and makes it available downstream; failure blocks it; `requiredSoakTime` on a freight source holds it for a time in the upstream stage. V: [verification](https://docs.kargo.io/user-guide/how-to-guides/verification).
- Argo Rollouts: AnalysisTemplate (metrics, interval, `successCondition`, `failureLimit`), run inline (blocks), in background, or pre/post promotion for blue-green; providers include `web` and Prometheus; Inconclusive pauses for a human. V: [analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/).
- Spinnaker Canary Analysis via Kayenta, analysis only. V: [stages reference](https://spinnaker.io/docs/reference/pipeline/stages/).
- GitLab `action: verify` exists as an environment job action (it does not reset `auto_stop_in`). V: [environments](https://docs.gitlab.com/ci/environments/).
- I: in all of them verification is **declared on the environment**, not on the pipeline run, and its result is **stored against the version**. A smoke test (send one real input, trace it in logs and events) is a job-type verification that fits Kargo's and Argo's job/web metrics; our Watcher window is a long, agent-read verification. Both can be two entries of one per-environment `verify` list: `smoke` (blocking, minutes) and `watch` (window, may roll back).

Its own `SDLC.md` does describe release lines `release/vX.Y.x`, `backport` labels and a hotfix that "may target `release/vX.Y.x` directly" with `backport main`, and says an agent never dispatches release workflows. V: clone at `7db6462`. That is a process for its own releases, not an engine feature.

## Proposed minimal concept set (I)

| Concept | Fields | Shape A (today) | Shape B |
|---|---|---|---|
| Environment | name, kind (`production` / `shared-test` / `ephemeral`), adapter, lock policy, verify list, rollback policy | `production` only | `test` (shared, occupancy lock), `production` |
| Version | immutable ref: git tag or SHA + image digest; source branch | main SHA after merge | PR tag (pre-merge) on `test`; release tag on `production` |
| Promotion | (version, environment, trigger, actor) → deployment record | Trigger: merge to main | Trigger: PR ready → `test`; tester approved + merged + release tag → `production` |
| Deployment record | env, version, started, ended, ok, verified, reason (`normal` / `rollback` / `hotfix`) | Exists in the state store | Same; plus holder of `test` |
| Gate | kind (human / rule), bound to (version or tree, environment), invalidated when the version changes | Merge gate before merge (R2), decision 25 rules (R0) | Tester gate on `test` before merge, bound to the tested tree; production gate by risk |
| Verification | per environment: `smoke` (blocking), `watch` (window, Watcher) | `watch` | `smoke` on `test` and `production`; `watch` on `production` optional |
| Rollback | `revert` (new version through the pipeline) or `redeploy-previous` (last verified version in that env) | `revert`; `redeploy-previous` when the culprit is unclear (decision 26) | `redeploy-previous` |
| Lock | `serialise` (one deploy at a time) or `occupancy` (holder + "free = equals production") | `serialise` | `occupancy` on `test`, `serialise` on `production` |

Shape B as a sequence, with the hotfix path:

1. Adapter `current(test)` ≠ `current(production)` and the holder is not this PR → stand occupied. Either wait/ask the holder, or, if the change is urgent, take the hotfix path (step 6).
2. Tag the PR branch → `deploy(test, tag)` → `wait` → `smoke`. Record holder = this PR.
3. Tester gate on (tag's tree, `test`). "Changes" → back to the Implementer; a new tag repeats 2–3.
4. Merge to `develop`; the stand stays held until the release lands or the PR is abandoned.
5. Release tag → check the release tree equals the approved tree for this service (or re-test) → `deploy(production, tag)` → `smoke` → optional `watch`. Red → `deploy(production, previous verified tag)`.
6. Hotfix when `develop` (or the stand) is ahead of production: branch from the production tag on `master`, cherry-pick only the fix, tag, deploy to production with smoke; bring the same change into `develop` by its own PR. This is git-flow's hotfix (branch from the production tag, merge into both `master` and `develop`; V: [nvie.com, 2010-01-05, note of 2020-03-05](https://nvie.com/posts/a-successful-git-branching-model/)) and cezar's backport-label variant (V, above).

What changes in the model (I): decision 8's "merge means deploy now" becomes the shape A value of "promotion trigger"; decision 26's revert-first becomes the shape A value of "rollback"; `.pipeline/project.yaml` `deploy.hook` becomes a list of environments, each naming an adapter (`shell`, `teamcity`, `helm`, `github-dispatch`, `dokploy`), a lock, a verify list and a rollback policy. The Merge gate and the tester gate are the same gate concept placed on different environments.

## Risks

- **Approved ≠ shipped** in shape B (I): the merge commit and the release build differ from the tested tag. Without a tree or digest check the tester gate is decorative.
- **Occupancy is a convention, not enforced** by any tool read (I): a human deploying from the CI UI bypasses the pipeline's lock. `current(test)` read from the cluster catches it after the fact; it cannot prevent it.
- **Redeploy-previous with a changed schema** breaks the older version (I, from the parallel-change precondition). Same expand–contract rule as decision 26.
- **Production ahead of `master` after a rollback** (I): the next release tag re-ships the fault unless the fix or revert is in it.
- **CI-server state is not deployed state** (I): a green "Deploy to Production" build says the job ended, not which image runs. `current(env)` must read the target.
- **Argo CD auto-sync blocks rollback** (V, above); Kargo auto-promotion would re-promote the newest freight without the 1.11 hold (V, Akuity post). An adapter on a GitOps target must pause automation before redeploying an older version.
- **Many repos, one stand** (I): occupancy is per service in the shared namespace, not per namespace; a lock on the whole namespace would serialise unrelated services.

## Open questions

1. Bind the tester's approval to an image digest (build once, promote the same image; needs the CI server to deploy by digest, not rebuild from the release tag) or to a git tree (rebuild allowed; needs a tree-equality check per service)?
2. Who releases the `test` hold: merge, the production deploy, a timeout, or the holder? A hold that never ends blocks everyone.
3. Is the tester gate one more human gate for the Operator's cap of waiting items (decision on "3 waiting"), or a separate role?
4. Does shape B keep the Watcher on production, or is the smoke test enough for a team that already has a human tester?
5. Should rollbacks and hotfixes emit CDEvents (`service.rolledback`) so DORA's rework rate can be computed outside the pipeline?
6. Not verified: TeamCity's REST representation of the "Deployments" section of a build; Spinnaker's record of who judged; the Dokploy deployment-listing endpoint; GitHub environment-level locks beyond `concurrency`; a named industry practice for occupancy of a shared stand.

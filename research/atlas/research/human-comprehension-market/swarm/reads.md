# Reads: Start Here and a possible "Comparisons and Talks" section

Ranked by what a reader gains in one evening. Entries already in the list (Osmani, the 3-tool dev.to test, Four bets) are not repeated.

## Candidates

- 🟢 [Deep Learning-based Code Reviews: A Paradigm Shift or a Double-Edged Sword?](https://arxiv.org/abs/2411.11401) - 2024 (ICSE 2025). Measured on people: a controlled experiment with 29 experts and over 50 hours of recorded reviews. Reviewers given an LLM review first focused on the places it pointed to, found more low-severity issues but no more high-severity ones, saved no time and were no more confident. *Limits: small programs, not agent pull requests; LLM review comments, not a map or a walkthrough.*
  - facts: arXiv 2411.11401, v3 2024-11 | source opened: yes (abstract) | from: found beyond lists (cited in the Copilot experiment below) | suggested sub-group: Research on Human Review. This is a controlled test of a tool on people, which the list currently says does not exist.
- 🟢 [Copilot Caught 8 of 8 Diff Bugs With Rules, 0 of 2 Outside the Diff](https://towardsdatascience.com/copilot-caught-8-of-8-diff-bugs-with-rules-0-of-2-outside-the-diff/) - 2026. Measured on an agent reviewer: ten seeded bugs in a synthetic billing service and a pandas pipeline, 28 public pull requests. Copilot review caught 5 of 8 bugs in the changed lines without written rules and 8 of 8 with them, and missed both bugs in unchanged code the change called, 0 of 4 runs each way on the main case, while recommending approval. *Limits: one author wrote both the bugs and the rules, some rules nearly name the bug; two out-of-diff cases; nothing measured on human reviewers.*
  - facts: article, public MIT repo per the author | source opened: yes | from: found beyond lists | suggested sub-group: Comparisons and Talks (hands-on test with numbers)
- 🟢 [AI Writes Faster Than Humans Can Review](https://arxiv.org/abs/2607.01904) - 2026. Measured on people, observational: 802 developers and 196,212 pull requests at one company under a "2x" mandate. Throughput rose about 12% when each developer started using AI and kept rising; review load per reviewer doubled and automated review passed human review in coverage within months. *Limits: one company, no randomized assignment; pull request count is a proxy for productivity, not for understanding.*
  - facts: arXiv 2607.01904, v3 2026-11, CMU and Stanford | source opened: yes (abstract) | from: found beyond lists (cited in a Semgrep post) | suggested sub-group: Research on Human Review
- 🟢 [Less is More: Supporting Developers in Vulnerability Detection during Code Review](https://arxiv.org/abs/2202.04586) - 2022 (ICSE). Measured on people: an online experiment with 150 participants. Simply asking reviewers to focus on security raised the probability of finding the vulnerability eight times; a security checklist, even one tailored to the change, did not improve it further. *Limits: human-written code and seeded vulnerabilities; says nothing about AI-written changes or tools.*
  - facts: arXiv 2202.04586, DOI 10.1145/3510003.3511560 | source opened: yes (abstract) | from: found beyond lists | suggested sub-group: Research on Human Review (a classic baseline for how much reviewers miss)
- 🟢 [Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) - 2025. Measured on people: a randomized trial with 16 maintainers on 246 issues in their own repos. With AI allowed they took 19% longer, yet expected a 24% speedup beforehand and still believed in a 20% speedup afterwards. *Limits: METR itself marks these results out of date; it measures time to finish, not understanding; the point for this list is that self-reports of "faster" are unreliable.*
  - facts: METR blog with arXiv paper; follow-up data 2026-02 | source opened: yes | from: found beyond lists | suggested sub-group: What the Evidence Says (perception gap)
- ⚪ [Programming as Theory Building](https://pages.cs.wisc.edu/~remzi/Naur.pdf) - Peter Naur, 1985. The program is the theory in its developers' heads, not the text; when the people who hold the theory leave, the code alone cannot bring it back. The root argument behind "comprehension debt" and "vibe code is legacy code". *Limits: an essay with case anecdotes, no measurement; written long before AI.*
  - facts: Microprocessing and Microprogramming, 1985; PDF hosted at wisc.edu | source opened: yes (PDF loaded) | from: found beyond lists | suggested sub-group: Start Here (classic)
- ⚪ [Vibe code is legacy code](https://stevekrouse.com/syndicated/vibe-code) - Steve Krouse, 2025-07. Code nobody understands already has a name, legacy code; vibe coding is a spectrum of how much you understand, and fine for throwaway apps. Short, and the fastest way into Naur's idea. *Limits: opinion; the author sells an AI coding product.*
  - facts: essay, originally on Val Town blog | source opened: yes | from: found beyond lists | suggested sub-group: Start Here
- ⚪ [The Final Bottleneck](https://lucumr.pocoo.org/2026/2/13/the-final-bottleneck/) - Armin Ronacher, 2026-02. Review is now the queue that overflows, as with 2,500 open pull requests on one project; since machines can't be accountable, humans have to understand the output, and throttling inflow is the only fix he sees today. *Limits: opinion, no data beyond the one pull request count.*
  - facts: blog post | source opened: yes | from: found beyond lists | suggested sub-group: Start Here
- ⚪ [Your job is to deliver code you have proven to work](https://simonwillison.net/2025/Dec/18/code-proven-to-work/) - Simon Willison, 2025-12. Moves the burden from the reviewer back to the author: attach a manual test with its commands and output, plus an automated test that fails if the change is reverted, and make the agent produce both. *Limits: opinion; proof of behaviour, not of design or of what the change touches outside the diff.*
  - facts: blog post | source opened: yes | from: found beyond lists | suggested sub-group: Start Here or What Did the Agent Just Change (pairs with Showboat by the same author)
- ⚪ [Getting AI to Work in Complex Codebases (No Vibes Allowed)](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md) - Dex Horthy, 2025. The written version of the "No Vibes Allowed" talk: review the agent's research and plan, not the 2,000-line diff, because a bad line of research becomes thousands of bad lines of code; review is for keeping the team's mental alignment. Includes a failed attempt. *Limits: experience report by a vendor of a tool for this workflow; numbers such as 35k lines in 7 hours are anecdotes, not a method.*
  - facts: stars 2836, created 2025-08, pushed 2026-10, licence none stated | source opened: yes (talk video page at youtube.com/watch?v=rmvDxxNubIg loaded without transcript) | from: found beyond lists | suggested sub-group: Comparisons and Talks
- ⚪ [From Technical Debt to Cognitive and Intent Debt](https://arxiv.org/abs/2603.22106) - Margaret-Anne Storey, 2026. Splits system health into three debts: technical debt in code, cognitive debt in people's shared understanding, intent debt in missing written rationale, with ways to diagnose and reduce each. Martin Fowler's [April 2026 fragment](https://martinfowler.com/fragments/2026-04-02.html) is a two-minute summary. *Limits: a position paper, no measurement.*
  - facts: arXiv 2603.22106, v4 2026-04, 10 pages | source opened: yes (abstract and the Fowler fragment) | from: found beyond lists | suggested sub-group: Do I Still Understand My Code or Start Here
- ⚪ [The Programmer's Brain](https://www.manning.com/books/the-programmers-brain) - Felienne Hermans, 2021, book. Cognitive science for reading unfamiliar code: working memory limits, misleading names, mental models, and onboarding that separates learning the domain from exploring the code. *Limits: draws on research but reports no new measurement; nothing on AI-written code.*
  - facts: Manning, 2021-08, 256 pages | source opened: yes (publisher page) | from: found beyond lists | suggested sub-group: Comparisons and Talks (books)
- ⚪ [Your Code as a Crime Scene, Second Edition](https://pragprog.com/titles/atcrime2/your-code-as-a-crime-scene-second-edition/) - Adam Tornhill, 2024, book. Reads a codebase through its git history: hotspots where complexity meets change, change coupling, and knowledge maps of who still understands which part. The method behind several hotspot and ownership tools. *Limits: the author founded CodeScene, which sells this analysis; case studies, no controlled evaluation in the book page.*
  - facts: Pragmatic Bookshelf, 2024-02, 336 pages | source opened: yes (publisher page) | from: found beyond lists | suggested sub-group: Comparisons and Talks (books)
- ⚪ [Augmented Coding: Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes) - Kent Beck, 2025. In augmented coding you still care about the code and its tests; lists the signs an agent is going off track (loops, unrequested features, deleting tests) and gives his TDD system prompt. *Limits: one project, one author; more about steering than understanding someone else's change.*
  - facts: newsletter post | source opened: yes | from: found beyond lists | suggested sub-group: Do I Still Understand My Code (lower priority)

# A read-only surface of the pipeline state

Research of 2026-11-25. Primary sources only: vendor documentation, specifications and source code. Every page was read on 2026-11-25. Archon was read in a shallow clone of [github.com/coleam00/Archon](https://github.com/coleam00/Archon) at `f9d1d2b` (commit date 2026-11-20); its documents are cited by repository path (`packages/docs-web/src/content/docs/...`; below, `reference/...`, `guides/...` and `getting-started/...` are under that folder). **V** = read in the source on that date; **I** = inferred by this note from verified facts. Extends [2026-11-supervisor-agent.md](2026-11-supervisor-agent.md), which settled what the Supervisor may do (decision 62); its findings on Cezar's manager, Archon's chat agent and AFactory are not repeated.

## Question

Decision 62 (`docs/decisions.md` of this repository) makes every read free for the Supervisor (items, states, queues, holds, releases, cost, provenance, traces) and puts every write on a route that checks who calls. Our `docs/STATUS.md` orders "a read-only surface of the pipeline state" before "caller identity on write routes". How do workflow engines and agent managers give a person and a supervising agent a read-only view of their state, and keep reads apart from writes? What does Archon already offer, and what should we build?

## Short answer

1. Every engine read has a **read path that is not a run**: Temporal Queries, Describe and Visibility; Kubernetes and Argo `get`/`list`/`watch`; GitHub `GET` endpoints; LangGraph `get_state` and thread history; Dagster GraphQL queries. None of them reads its own state by starting a workflow. (V)
2. Reads are separated from writes in two places at once: **by the operation** (a query handler that must not mutate, HTTP `GET` versus `POST`, GraphQL query versus mutation) and **by the identity** (a read-only role: Temporal Cloud "Read-Only" and namespace "Read", Kubernetes `view`, Argo CD `role:readonly`, GitHub `read` permissions, Dagster+ "Viewer"). Several also offer a **UI switch** that removes writes (Temporal Web UI `disableWriteActions`). (V)
3. Agent tool servers follow the same rule: GitHub's MCP server has a read-only mode that drops write tools "even if they were requested"; the Kubernetes MCP server says the access control to rely on is RBAC on its own identity, and calls its read-only flag a "best-effort guardrail". MCP's `readOnlyHint` is a hint, and the spec says clients must not decide on it for untrusted servers. (V)
4. Archon already has most reads, over HTTP and the CLI: items (`GET /api/items`, `/api/items/window`), runs with node state, owner liveness, provider events and artifacts, the attention queue and its stream, the dashboard, metrics and pack-declared metric cards, and the install hold inside status and item reads. (V)
5. Archon lacks three things: **no HTTP read of the state store** (`archon state get/list` is CLI only, and our pipeline keeps work, releases, release gates, findings and provenance there); **no read-only role** (roles are operator, admin, member; "Reads remain open", and the CLI is always the local operator, so a shell with `archon` can approve); **no MCP server of its own** (its chat tools run in-process and mix reads and writes in one `manage_run` tool). (V)
6. Running a workflow to read state is an anti-pattern here: in Archon it writes a run record, takes a resource slot, waits behind the install hold (when the Operator most needs to read) and is serialised per item. No engine read does this. (V for Archon's admission rules, I for the conclusion)
7. Our pick: a small **read-only MCP server in our pack** that calls only Archon's `GET` routes and an allowlist of read CLI subcommands, with no write tool in it at all, under its own identity; ask upstream for an HTTP state read and a read-only role, and drop the CLI part once those exist. (I)

## 1. Temporal

- **Queries are reads; Signals and Updates are writes.** Queries are "read requests" that "can read the current state of the Workflow but cannot block"; they "never add entries to the Workflow Event History" and "can operate on completed Workflows". Signals are "asynchronous write requests"; Updates are "synchronous, tracked write requests", may be validated before acceptance, and an accepted Update writes to history. V: [workflow message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing).
- **A query handler must not mutate.** Python SDK: "A Query handler returns a value: it can inspect but must not mutate the Workflow state"; it "uses `def`, not `async def`"; no activity can run in it. V: [Python message passing](https://docs.temporal.io/develop/python/message-passing).
- **Visibility for lists, Describe for one.** Visibility lists and counts executions with a SQL-like List Filter over search attributes; it is updated asynchronously and is eventually consistent, with no SLA in Cloud; "Visibility is built for finding and filtering across many executions, not for reading the current state of one execution", for which `DescribeWorkflowExecution` is named. V: [Visibility](https://docs.temporal.io/visibility).
- **CLI reads.** `temporal workflow describe`, `list`, `count`, `show` (event history), `query`, `stack`, `trace`, `result`, `metadata`; writes are `signal`, `update`, `cancel`, `terminate`, `reset`. The page does not group them; the split is ours from each description. V / I: [temporal workflow](https://docs.temporal.io/cli/workflow).
- **Web UI read-only switch.** `disableWriteActions` (`TEMPORAL_DISABLE_WRITE_ACTIONS`) disables "every action in the Web UI that changes a Workflow Execution or Activity, including batch actions", overrides the per-action keys, and "The Web UI Server also rejects write requests to its HTTP API". Per-action keys exist for terminate, cancel, signal, reset and batch actions. V: [Web UI configuration](https://docs.temporal.io/references/web-ui-configuration).
- **Read-only identity.** Temporal Cloud has an account role "Read-Only" ("Can read information") and a namespace permission "Read" ("Can only read information from the Namespace"), against "Write" and "Namespace Admin". V: [Cloud users](https://docs.temporal.io/cloud/users). An API key is "a unique identity linked to role-based access control (RBAC) settings", checked as key, then identity (user or service account), then RBAC. V: [API keys](https://docs.temporal.io/cloud/api-keys). So a read-only service account with its own key is the read identity (I).

## 2. Kubernetes and Argo

- **Verbs.** `GET`/`HEAD` map to `get`, `list` and `watch`; `POST` to `create`, `PUT` to `update`, `PATCH` to `patch`, `DELETE` to `delete`/`deletecollection`. V: [authorization](https://kubernetes.io/docs/reference/access-authn-authz/authorization/).
- **Read-only roles.** A Role with `verbs: ["get", "watch", "list"]` reads; RBAC is purely additive, "there are no 'deny' rules". The default `view` ClusterRole "Allows read-only access to see most objects in a namespace", excludes roles and bindings, and excludes Secrets because reading them "enables access to ServiceAccount credentials" (privilege escalation). V: [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/). Consequence: a read-only identity must also be kept from reading anything that is itself a credential (I).
- **Argo Workflows.** CLI reads `argo get`, `list`, `logs`, `watch`, `wait`; writes `submit`, `retry`, `resubmit`, `stop`, `terminate`, `suspend`, `resume`, `delete`. V: [argo CLI](https://argo-workflows.readthedocs.io/en/latest/cli/argo/). The Argo Server acts with its own service account, the client's bearer token, or SSO ([auth modes](https://argo-workflows.readthedocs.io/en/latest/argo-server-auth-mode/)); with SSO RBAC each user is mapped to a service account by an `rbac-rule` expression, and the documented default is a `read-only` service account matching every user at the lowest precedence; no match is denied. The docs leave the account's Role to the operator. V: [Argo Server SSO](https://argo-workflows.readthedocs.io/en/latest/argo-server-sso/). The UI has no read-only mode of its own; read-only comes from the identity (I).
- **Argo CD** ships `role:readonly` ("read-only access to all resources") and suggests `policy.default: role:readonly`, so every signed-in user reads and nothing more by default. V: [Argo CD RBAC](https://argo-cd.readthedocs.io/en/stable/operator-manual/rbac/).

## 3. GitHub Actions and the REST API

- Runs: `GET /repos/{owner}/{repo}/actions/runs` and `GET .../actions/runs/{run_id}` need the fine-grained "Actions" permission **read**; `POST .../runs/{run_id}/cancel` and `.../rerun` need **write**. Deployments: `GET /repos/{owner}/{repo}/deployments` needs "Deployments" **read**, `POST` the same path needs **write**. V: [fine-grained token permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens), [workflow runs](https://docs.github.com/en/rest/actions/workflow-runs), [deployments](https://docs.github.com/en/rest/deployments/deployments).
- In workflows, each `GITHUB_TOKEN` permission is `read`, `write` or `none`, "`write` includes `read`", and `permissions: read-all` or `{}` set all at once. V: [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax); least privilege is recommended at [automatic token authentication](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication).
- So a read-only token is a token whose every permission is `read`; the server, not the client, refuses a write (I).

## 4. LangGraph, Dagster, Inngest

- **LangGraph.** `graph.get_state(config)` returns the latest state; `get_state_history(config)` returns the thread's `StateSnapshot`s. `update_state` "creates a new checkpoint with the updated values", and "The update is treated the same as a node update", attributed through `as_node`. V: [checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers). Over HTTP the agent server has `GET /threads/{thread_id}/state` (latest checkpoint) and `GET /threads/{thread_id}/history` ("Get all past states for a thread") against `POST /threads/{thread_id}/state` ("Add state to a thread"). V: [get state](https://docs.langchain.com/langsmith/agent-server-api/threads/get-thread-state), [history](https://docs.langchain.com/langsmith/agent-server-api/threads/get-thread-history), [update state](https://docs.langchain.com/langsmith/agent-server-api/threads/update-thread-state). A write to state is a recorded step, never a side effect of a read (I).
- **Dagster.** One GraphQL endpoint; reads are queries (`runsOrError` with a filter by status, job, tags; `logsForRun`), writes are mutations (`launchRun`, `terminateRun`); a Python client wraps it. V: [GraphQL API](https://dagster.io/docs/api/graphql). Dagster+ "Viewer" is the least permissive role: it sees runs and deployments but cannot launch, re-execute, terminate or delete runs, or start schedules. V: [user roles](https://dagster.io/docs/deployment/dagster-plus/authentication-and-access-control/rbac/user-roles-permissions).
- **Inngest** has a REST API over "events, function runs, environments, and more" (v1 and v2, OpenAPI at `api-docs.inngest.com/api-specs/v2.json`) and a dashboard that searches runs by CEL expressions. V: [API docs](https://api-docs.inngest.com/), [inspecting runs](https://www.inngest.com/docs/platform/monitor/inspecting-function-runs). Its per-endpoint read/write split was not read (not verified).

## 5. Agents reading state

- **MCP annotations are hints.** `readOnlyHint`: "If true, the tool does not modify its environment" (default `false`); `destructiveHint` defaults `true`, `idempotentHint` `false`, `openWorldHint` `true`; "all properties in ToolAnnotations are **hints**", "not guaranteed to provide a faithful description", and "Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers". V: [schema.ts 2025-11-25](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-11-25/schema.ts). The tools page repeats that clients "MUST consider tool annotations to be untrusted unless they come from trusted servers", and that servers "MUST ... Implement proper access controls". V: [tools, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools). For read-only data MCP also has resources, "A known resource that the server is capable of reading". V: [schema](https://modelcontextprotocol.io/specification/2025-11-25/schema).
- **GitHub MCP server.** A read-only mode (`--read-only` / `GITHUB_READ_ONLY` locally, `X-MCP-Readonly` header or `/readonly` path remotely) is "a strict security filter that takes precedence over any other configuration, by disabling write tools even when explicitly requested". V: [server configuration](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md). How it classifies a tool as read-only was not read (not verified).
- **Kubernetes MCP server.** "Kubernetes RBAC on the identity this server authenticates as is the access control to rely on"; its `read_only` and `denied_resources` settings are "best-effort guardrails"; production setup uses a dedicated ServiceAccount with read-only access. V: [containers/kubernetes-mcp-server](https://github.com/containers/kubernetes-mcp-server).
- **A top agent's reads in a real orchestrator.** Gas Town's Mayor works with `gt convoy list`/`show`, `gt agents`, `gt escalate list`, `gt scheduler status` and the `gt feed` terminal view; its web dashboard (`gt dashboard`) has a command palette that runs `gt` commands, and `gt feed` has nudge and hand-off keys, so neither view is read-only. V: [steveyegge/gastown](https://github.com/steveyegge/gastown). Cezar's manager reads through its own CLI and read-only `gh`, fenced by a shell allowlist ([engines-code.md](supervisor/engines-code.md)). Pattern: top agents read through the orchestrator's own list/show commands; where a view mixes reads and controls, the separation comes from what the agent can reach, not from the view (I).

## 6. Archon (the engine we use)

### Reads that exist

| What the Supervisor reads | Archon read | HTTP | CLI |
|---|---|---|---|
| An item: its runs (status, outcome, cause, spend), queued and skipped starts and what each waits behind, open questions, answers, rulings, links, merge, landing branch, the install hold | item read | `GET /api/items?project=&key=` | `archon workflow runs --item <key> --json`; `--item-of <run-id>` |
| Items with a run in a window, a page at a time | items window | `GET /api/items/window` | `archon workflow items` |
| Runs and their node state, owner liveness | runs | `GET /api/workflows/runs`, `GET /api/workflows/runs/{runId}`, `GET /api/dashboard/runs` | `workflow status`, `runs`, `get`, `--open` |
| Traces | provider events, artifacts, logs | `GET .../runs/{runId}/provider-events`, `GET /api/runs/{runId}/artifacts`, `GET /api/artifacts/{runId}/{filename}` | `workflow logs`, `artifacts` |
| What waits for a person | attention queue | `GET /api/runs/attention` (+ `/stream` SSE), `GET /api/runs/{runId}/attention` | `workflow attention` |
| Cost and figures | metrics, pack cards | `GET /api/metrics`, `GET /api/metric-views` | `archon metrics`, item metrics per pack |
| The install hold and held starts | hold | inside the item read (`hold`, `held`) | `workflow status --json` (`hold`, `heldStarts`) |
| Stage graph of a pack | pack graph | `GET /api/packs/{pack}/graph` | `archon pack graph --json` |
| Durable state documents (ours: `work/<key>`, `findings/<id>`, `releases-line`, `release-gates/<id>`, `provenance/<key>`, `ledger/<item>`) and their leases | state store | **none** | `archon state get`, `list [--values]`, `log` |

V: `reference/api.md` (Workflows/Runs, Attention queue, Dashboard, Metrics), `reference/cli.md` (`workflow status`, `workflow runs`, `workflow items`, Items, `hold`, state), `guides/metrics.md` ("Reading metrics", "Overview cards a pack declares", "Item metrics a pack declares"). The server's route files (`packages/server/src/routes/`) have no state route, and the API reference names none (V). The state document names are from our `implementations/archon/` (V).

Details that matter:

- The item read "reports recorded facts only; it computes no stage for the item" (`reference/cli.md`, `workflow runs`). Our stage lives in `work/<key>`, which only the CLI reads (V, I).
- Every revision a state read returns carries its `lease` (`{runId, nodePath, takenAt, live}`), so leases (our locks) are readable through `state get`/`list` (V, `reference/cli.md`, state).
- An OpenAPI 3.0 document is served at `GET /api/openapi.json` (V, `reference/api.md`).
- **Packs can declare console views, but only metrics:** `<pack>/.shared/metric-views.json` (one to six cards of shapes `count`, `ratio`, `cost_per`, "display only") and `<pack>/.shared/item-metrics.json` (`share`, `count`, `duration` over items). No other pack-declared console view was found (V, `guides/metrics.md`; a search of the docs finds no other `.shared/*.json` view file).
- Some "reads" write: `archon state` outside a run resolves the project from the current checkout, "auto-registered when needed", unless `--project <key>` names it; `archon project config` opens the store and on a fresh install creates the database; `GET /api/providers/opencode/credentials` "starts the embedded runtime on demand". (V, `reference/cli.md`, `reference/api.md`)

### Identity and roles

- Roles are `admin` and `member`, plus the local operator. "Approve, reject, respond, resume, cancel, abandon, signal and delete are authorized in core operations ... Reads remain open." A member may act only on runs it started; an unidentified caller is refused. "The CLI is always the local operator. The console with web auth off and no resolved identity is also the operator." V: `reference/security.md` ("Users and roles", "Who can act on a run").
- There is **no read-only role**: a member can still create conversations and start runs (V, same page and `reference/api.md`). Recording or withdrawing a ruling needs the operator or an admin (V, `reference/api.md`, `/api/items/rulings`).
- A CLI write to the state store outside a run is recorded as `{kind: "surface", via: "cli"}`: "the surface the write came through, not who made it" (V, `reference/cli.md`, state). The CLI identity is `ARCHON_USER_ID`, else `$USER` (V, `reference/cli.md`, `ai` and `hold`).
- With web auth on, every `/api/*` call needs a session or the trusted `X-Archon-User` header, which a proxy must strip from clients (V, `reference/security.md`, `reference/api.md`).
- Consequence: giving an agent the `archon` binary or an unauthenticated port gives it the Operator's write authority; reads cannot be separated from writes by identity in Archon today, only by what the agent can reach (I).

### Agents and Archon

- Archon has **no standalone MCP server**. Its chat agent gets native tools (`invoke_workflow`, `register_project`, `manage_run`, `attention`), exposed to Claude through an in-process SDK MCP server named `archon` (V, `getting-started/ai-assistants.md`; `packages/providers/src/claude/native-tools.ts`, which registers each tool with a description and schema and no annotations).
- `manage_run` is one tool whose `action` is one of `help`, `list`, `get`, `resume`, `cancel`, `abandon`, `approve`, `reject`, `respond`, `label`; destructive actions need `confirm=true` (V, `packages/core/src/orchestrator/manage-run-tool.ts`). Reads and writes share one tool, so no client can grant only its reads (I).
- The documented way for other agents is the CLI: Copilot and OpenCode chats run `archon workflow run <workflow> "<message>" --detach` in the project directory, as the CLI identity (V, `getting-started/ai-assistants.md`); inside a node, `archon state` resolves the run from `WORKFLOW_ID` (V, `reference/cli.md`).

### What a run costs if used to read

- A hand start or binding start goes through admission: resource capacity, overlap policy, queue order (V, `guides/workflow-triggers.md`, "Choose a resource, capacity, and overlap policy").
- While the install hold is set, "admission admits no new run from any source"; a hand start "creates its `pending` run and waits for the lift" (V, `reference/cli.md`, `hold`).
- "One item is worked by at most one run of a workflow at a time" (V, `reference/cli.md`, Items).
- Every run is a row in run lists, the dashboard and the item's history, and its cost and outcome feed metrics (V for the lists, `reference/api.md`; I for the noise).

## What this means for us (I)

**The common pattern.** Reads are served by the engine's own query surface (an API, a CLI, a UI) under an identity that can only read; the server refuses writes from it. Annotations, UI switches and tool lists are a second layer, never the only one. No engine reads its own state by starting a workflow: Temporal's read path is defined by not touching history, Kubernetes reads are `GET`, LangGraph's writes to state are explicit checkpoints.

**Running a workflow to read is an anti-pattern for us.** In Archon it creates a run record, takes a slot, waits behind the install hold and behind another run of the same workflow on the item, starts a process, and adds rows to every run list and metric. It is slowest exactly when the Operator pauses the install to look.

**Options, best first:**

1. **A read-only MCP server in our pack** (a thin adapter, no state of its own). Tools that call only Archon's `GET` routes (items, items window, runs, run detail, provider events, artifacts, attention, dashboard, metrics, metric views, pack graph) and an allowlist of CLI reads for what has no route (`state get`, `state list --values`, `state log`, always with `--project <key>`, and `workflow status --json` for the hold). Every tool `readOnlyHint: true`, but the guarantee is that the server contains no write path and its process holds no write credential. Plus a few composed reads that answer the Operator's questions directly (an item's stage from `work/<key>` beside its runs; the release line with gates; cost per item from `spend`). Gains: works today, one surface for the Supervisor and for a person (the same tools back a console page or a CLI), reads are free and fast, no runs. Costs: the CLI part runs as the local operator, so the adapter's allowlist is the only fence for those calls until Archon has a state read route; the adapter must be kept in step with Archon's read contracts.
2. **Upstream: an HTTP read of the state store and a read-only identity in Archon** (`GET` state routes; a role that reads and cannot start runs, answer, or write state). Gains: the fence moves into the engine, as in every system above; the CLI part of option 1 goes away. Costs: depends on the maintainer; until it lands, option 1 is still needed. Worth filing as a request together with the caller-identity work.
3. **Pack-declared metric cards** (`metric-views.json`, `item-metrics.json`) for the console. Gains: no code, already rendered by Archon. Limits: metrics only, one to six cards; no items, holds, releases or traces. A complement, not the surface.
4. **Direct read of the engine's database** under a read-only database role. Gains: complete and fast. Costs: the schema is not a published contract; it bypasses the engine's projections (owner liveness, `degraded` parts, lease `live`), so the answers can be wrong in exactly the cases that matter.
5. **A status workflow that reads and reports.** Rejected for the reasons above.

**Pick: option 1 now, option 2 asked upstream.** It follows the pattern every engine uses (the engine's own reads, behind a surface that cannot write), it needs nothing new from Archon, and it gives decision 62 its "free reads" as a separate tool set: the Supervisor's write tools then live elsewhere and go through the caller-identity routes, so no single tool mixes the two, unlike `manage_run`. The read server must never offer a generic `archon` passthrough or shell; it must not read secrets (the Kubernetes `view` lesson: Archon's credential routes and env values stay out); and cross-project reads stay read-only by construction.

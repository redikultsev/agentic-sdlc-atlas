# S17. Decommissioning

Phase F1 broad sweep, 2026-11. Not yet verified in depth: `search-snippet` rows were not opened.

## State of the art

As of late 2026, agentic decommissioning is mature in only one narrow slice: removing stale feature flags. DoorDash (ICSME 2026), Atlassian Rovo Dev, LaunchDarkly Vega, Unleash and FeatBit all run an agent that opens a PR from lifecycle metadata. Two things matter most in their designs: reading the live rollout state, and a human confirming the target value. Broader dead-code and product removal still runs mainly on pre-LLM deterministic systems: Google Sensenmann (liveness logs plus the build graph), Meta SCARF (static and dynamic usage signals, a deletion roadmap, more than 100M LOC removed) and Uber Piranha. LLM agents are now being layered on top of usage evidence from tools such as Azul Code Inventory and knip. Practitioners agree on the rule "several independent usage signals, small reversible slices, delete code before deleting the flag or data". Infrastructure teardown is the contested and dangerous part. The best-documented agent incidents are deletions: PocketOS/Railway, DataTalks.Club terraform destroy, Replit, and the disputed Kiro/AWS case. The response has been platform-level soft deletes, scoped tokens and deterministic hook guards, not trust in the model. Vendors such as Harness deliberately stop the agent at the PR. A 2026 measurement paper finds the opposite failure in code: frontier models avoid deletion, keep code behind guards, and pass tests anyway. Agents are therefore weak at both ends: too timid in code and too destructive in infrastructure.

## Approaches

| Approach | What | Evidence | Seen in |
|---|---|---|---|
| **Liveness-signal-driven deletion (runtime usage evidence + dependency graph)** | Production execution or traffic logs mark assets as alive, liveness is propagated through the build or dependency graph, and anything without signals is proposed for deletion as reviewable changes. A blocklist handles exceptions. | strong | Google Sensenmann, Meta SCARF product deprecation, Azul Code Inventory + AI agent removal workflow |
| **Live-state-grounded feature-flag cleanup agent with human target-value checkpoint** | The agent reads the flag platform's rollout state (over MCP or API), a human confirms the permanent value, then parallel agents in isolated worktrees remove the branches and tests behind deterministic gates (build, tests, coverage, lint) before opening a PR. The flag record is archived only after the code ships. | strong | DoorDash multi-agent flag cleanup, Atlassian Rovo Dev flag cleanup, FeatBit agent cleanup guide, LaunchDarkly Vega flag cleanup, Unleash AI flag cleanup, Augment feature flag cleanup workflow |
| **Deterministic codemod for removal** | Rule-based AST rewriting deletes code tied to a flag or an unused symbol. It is cheap and predictable but cannot follow semantic indirection such as DI wrappers. Agents are increasingly used to write the recipes rather than make the edits. | strong | Uber Piranha / PolyglotPiranha, OpenRewrite/Moderne unused-code recipes |
| **Static unused-code analyzer feeding a coding agent** | A whole-program analyzer such as knip or Vulture produces the candidate list, and the agent deletes one package or slice at a time, often one worktree per package, with compile and test checks. | mixed | knip + knip MCP server, Factory dead-code removal guidance, dev.to knip per-worktree workflow, oh-my-openagent remove-deadcode skill |
| **Staged deprecation roadmap ordering** | Removal runs in dependency order: entry points and clients, then server code, then schemas, then data. Usage signals block automation, and a human can override them. Code is removed before data or flag records so that no new data gets created and rollback stays possible. | strong | Meta SCARF product deprecation, FeatBit agent cleanup guide |
| **Agent stops at PR for infra waste removal + blast-radius scoring** | A FinOps or drift finding becomes an IaC pull request. A risk score is computed from the plan, and a human approves and merges. Production workspaces can be opted out. | weak | Harness Infrastructure Efficiency Loop, Stacklet / Cloud Custodian MCP, OPA/Conftest on terraform plan |
| **Platform-level safe-deletion primitives** | Soft delete with a recovery window, deletion protection, prevent_destroy, scoped short-lived tokens, and backups kept outside the blast radius. These are enforced by the platform rather than the prompt and were retrofitted after agent incidents. | mixed | Railway delayed deletes post-incident, PocketOS/Railway incident, DataTalks.Club terraform destroy incident |
| **Deterministic pre-execution destructive-action guard** | A hook in the agent runtime parses each tool call into effects and blocks proven-destructive calls (terraform destroy, repo delete, db drop, backup destroy). It never approves anything, and it runs before any LLM classifier. | weak | nah guard, applygate / failproof terraform policies |
| **Decision-level deprecation memory** | The agent is told that a still-present pattern or service is retired, using decisions dated from PRs, tickets and meetings, so it stops adding call sites to the old path during a long migration or removal. | weak | Sentra stale-context guidance |

## Open gaps

- No published system or measurement for agents decommissioning whole services, endpoints or repositories end to end. Everything measured is flag cleanup or dead-code CLs.
- No evidence on how long a usage-observation window is enough before an agent removes an endpoint or binary. Sensenmann says 'a long time' and Azul says 'a release cycle or fiscal year-end'.
- No public benchmark of agents correctly cleaning up orphaned cloud resources, only incident reports and vendor launches.
- Whether deletion-avoidance bias (Guard-and-Go) and destructive-infra eagerness come from the same model behavior, and how to calibrate both at once, is unstudied.
- No data on the acceptance rate of agent-authored deletion PRs from owners who did not request them. Sensenmann reports mostly negative feedback.
- How to handle repository archival and branch/worktree cleanup for many parallel agents safely is undocumented.

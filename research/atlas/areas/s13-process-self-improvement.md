# S13. Process self-improvement

Phase F1 broad sweep, 2026-11. Not yet verified in depth: `search-snippet` rows were not opened.

## State of the art

As of late 2026 the agent pipeline usually improves itself without touching model weights. Changes go into text artifacts: rules files, skills, memory stores and playbooks. Four loops recur: (1) corrections captured in a session become rules or skills, either through a human-reviewed queue or a PR to a skill file; (2) offline "dreaming" or retrospective passes over transcripts that consolidate, correct and prune memory; (3) production failures turned into replayable regression evals that gate later harness changes; (4) recurring corrections pushed down into deterministic checks (lint, types, hooks, architecture) instead of prose. The best-supported evidence is mostly negative or cautionary. Context files often do not raise success rates and cost about 20% more inference. Instruction files grow without bound because deleting a rule is risky once its reason is lost. Stale instructions add cost that task-success metrics do not show. Self-written skills do not help on average. Self-evolution adds a backdoor attack surface. Vendor systems (Copilot memory, Cursor Bugbot learned rules, Factory Signals, Devin/Claude dreaming, Warp improver skills) report gains, but these are self-reported. The point still argued over is whether the agent should write its own lessons or whether every candidate must pass a measurement gate (replay with and without it, held-out non-regression) with a human merge. Mature practitioners and the stronger papers converge on gated admission plus pruning.

## Approaches

| Approach | What | Evidence | Seen in |
|---|---|---|---|
| **Correction capture to rules file** | Detect user corrections in-session (regex or LLM classifier), queue them, and append them as rules to CLAUDE.md/AGENTS.md, usually after human review. Cheap and popular. Its known failure is unbounded growth and stale rules. | weak | claude-reflect, Self-Improving AI Coding Agents Through Accumulated Behavioral Rules, Compound Engineering plugin (Every), Devin Memory and Dreaming |
| **Measurement-gated admission and pruning** | A candidate rule or skill is admitted only when replaying the failing scenario shows a gain with it versus without it and a regression suite or held-out split shows no harm. Existing text gets the same test before deletion. Some setups cap the playbook size. | mixed | Cortex, Post-mortem loop with replay admit gate (dev.to), Recursive Self-Evolving Agents via Held-Out Selection (RSEA), Cursor Bugbot learned rules |
| **Offline consolidation / dreaming over transcripts** | A scheduled background pass reads past session transcripts and the memory store. It dedupes, corrects notes against ground truth, prunes unused entries, builds indexes or wikis, and decides which small set of entries is injected every session. | mixed | Anthropic: The components of agent memory, Claude Managed Agents Dreams, Devin Memory and Dreaming |
| **Just-in-time verified memory with citations** | Memories are stored with code-location citations and re-verified against the current branch before use. Contradicted memories are rewritten instead of curated offline. | mixed | GitHub Copilot agentic memory |
| **Session-level friction analytics feeding a fix loop** | An LLM judge extracts facets and friction from many sessions (rephrasing, rejected tool calls, context churn) and correlates them with releases. Above a threshold it files tickets that an agent fixes, with a human approving the merge. The single-user version produces a report and suggested CLAUDE.md rules. | weak | Factory Signals, Claude Code /insights |
| **Improver agent editing skills via PR** | An outer scheduled improver skill reads accumulated human feedback on an inner skill's outputs and opens a small PR editing the inner skill. A human reviews it like any code change. | weak | Warp self-improving agents on Claude, Letta Skill Learning |
| **Incidents to regression evals (error analysis)** | Read traces, label pass/fail with a critique, cluster failures into cohorts, write one cheap evaluator per cohort, and replay the cohort after every change to prompt, tool or model. These suites become release gates. | mixed | Anthropic: Demystifying evals for AI agents, Decoding AI: error analysis to regression suite (Kitaru), LangSmith Engine / production traces to datasets |
| **Push corrections down the enforcement pyramid** | Instead of adding prose, turn a repeated correction into a codebase or API change, a lint rule, a type, a test or a hook. Prose is kept for judgment calls only. This answers rule decay directly: the agent cannot argue with CI. | weak | Lauren Tan: All Code Is Slop (Except Mine), Claude Code issue: hard-enforce CLAUDE.md rules via hooks |
| **Evolving playbooks (ACE family)** | Context is a structured, itemized playbook updated incrementally by generator, reflector and curator roles. The incremental updates are meant to avoid the brevity bias and collapse that wholesale rewrites cause. Follow-ups add retrieval over large playbooks and RL training of the reflect/curate roles. | mixed | Agentic Context Engineering (ACE), ACE retrieval over playbooks blog, Experience-Handoff RL (ACE-RL), GEPA |
| **Self-modifying agent scaffold** | The agent edits its own harness code or tools and is benchmarked, keeping the better variants (open-ended archive or live during a task). | mixed | Darwin Godel Machine, Live-SWE-agent |

## Open gaps

- No controlled study compares, on one real repo, prose rules vs lint/hook enforcement vs no learning for the same recurring correction.
- No cheap, solo-scale method decides when a rule should be retired. Cortex tests deletions but found nothing on a real repo with few corrections, and the practitioner cap-and-retire-cold approach is heuristic.
- How should learnings be shared or isolated across many parallel agents and across personal vs employer repos, including leakage of private conventions into global memory? Only Devin's git-merge design touches this.
- Do memory and rule gains shrink as models get stronger? Cortex saw little gain with Sonnet 5, and Anthropic found prescriptive memory rules hurt stronger models. Nobody tracks this across model upgrades.
- How do you evaluate the process itself (throughput, rework, revert rate, human minutes per merged PR) for one developer, as opposed to per-task benchmarks? Mostly vendor dashboards cover this.
- How can a stale rules file be detected automatically, beyond checking paths, for example by verifying that commands and claims still hold, the way Copilot verifies citations for memories?
- How should provenance and trust filtering of inputs into the learning loop work in practice (SkillJack-style poisoning from issues or web content)?

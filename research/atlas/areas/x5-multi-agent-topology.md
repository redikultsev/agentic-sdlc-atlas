# X5. Multi-agent topology

Phase F1 broad sweep, 2026-11. Not yet verified in depth: `search-snippet` rows were not opened.

## State of the art

As of late 2026 practice has settled on a narrow set of multi-agent shapes for software work. One is a single writer with extra read-only or advisory agents: subagents, a clean-context reviewer, a "smart friend" model. The other is hierarchical map-reduce, where a manager or planner hands isolated tasks to workers who run in separate git worktrees or containers and integrate by branch-and-merge with test gates. Flat self-coordinating swarms using shared files and locks failed in both Cursor's and Anthropic's experiments. Cognition, which wrote "Don't Build Multi-Agents" in 2025, partly reversed itself in April 2026, but still says writes should stay single-threaded. Controlled studies (Google's 180-configuration scaling study, MAST, NP-Bench) agree that multi-agent setups help on parallelizable, verifiable work and hurt on sequential, tool-heavy work, that uncoordinated parallel agents amplify errors, and that most failures come from coordination and verification, not from any single agent. Two things remain contested. First, whether the large-swarm demos (Cursor's browser, Anthropic's C compiler) carry over to real software without a simple oracle: the browser drew a public backlash for not compiling. Second, whether role-play "software company" frameworks (MetaGPT, ChatDev) have any production relevance beyond research.

## Approaches

| Approach | What | Evidence | Seen in |
|---|---|---|---|
| **Planner/manager - workers - judge hierarchy** | A manager agent decomposes the goal into tasks, fresh-context workers execute them, and a judge or validator decides whether to continue or re-plan. Workers do not coordinate with each other. | mixed | Cursor: Scaling long-running autonomous coding, Factory Missions, Cognition: Multi-Agents: What's Actually Working, Composio Agent Orchestrator, Gas Town + Beads, Claude Code agent teams |
| **Flat self-coordination via shared state and locks** | Peer agents claim tasks from a shared file or board using locks or optimistic concurrency, with no hierarchy. Cursor reports this failed: lock bottlenecks, and agents became risk-averse and avoided hard tasks. | mixed | Cursor: Scaling long-running autonomous coding, Claude Code agent teams |
| **Single writer plus read-only or advisory agents** | Only one agent writes. Other agents add intelligence without writing: a clean-context reviewer, a 'smart friend' advisor model, or search subagents. | mixed | Cognition: Multi-Agents: What's Actually Working, Cognition: Don't Build Multi-Agents |
| **Task ledger outside context (issue DB as coordination substrate)** | Work items, dependencies and agent identity live in a git-backed or SQL ledger that agents query, so state survives sessions and is shared across agents. | weak | Gas Town + Beads, Claude Code agent teams |
| **Learned or predicted orchestration topology** | Choose the architecture (single, centralized, decentralized) from task properties, or train an orchestrator with RL to sequence agents. | mixed | Towards a Science of Scaling Agent Systems, Multi-Agent Collaboration via Evolving Orchestration (Puppeteer), Single-agent or Multi-agent Systems? Why Not Both? |
| **Single writer plus advisory agents** | One agent owns all writes. Other agents add intelligence without acting: read-only search subagents, a clean-context reviewer looping with the coder, or a stronger 'smart friend' model it can consult. | mixed | Cognition: Multi-Agents: What's Actually Working, Cognition: Don't Build Multi-Agents, Claude Code parallel-work surfaces (subagents, agent view, agent teams, dynamic workflows), Reddit: 1 vs 2 agents on SWE-bench (coder + reviewer) |
| **Hierarchical planner/worker (map-reduce-and-manage)** | A root planner, optionally with recursive subplanners, creates tasks. Workers run in isolation and report back through handoffs. Judge or integrator roles were often added and later removed as bottlenecks. | mixed | Cursor: Scaling long-running autonomous coding, Cursor: Towards self-driving codebases, CAID (Geng & Neubig), Gas Town, Augment Intent, Cognition: Multi-Agents: What's Actually Working |
| **Flat peer swarm with shared state and locks** | Equal agents claim tasks through a shared file or lock files and merge on their own. It works when the oracle is very good and the tasks are independent. It degraded through lock contention, risk aversion and duplicated work. | mixed | Anthropic: Building a C compiler with a team of parallel Claudes, Cursor: Scaling long-running autonomous coding, Cursor: Towards self-driving codebases |
| **Isolation plus branch-and-merge with test-gated integration** | Each agent gets its own worktree, container or VM. Work is merged through git, with CI or test suites as the arbiter, sometimes behind a Bors-style bisecting merge queue. | strong | CAID (Geng & Neubig), Gas Town, Anthropic: Building a C compiler with a team of parallel Claudes, Claude Code parallel-work surfaces (subagents, agent view, agent teams, dynamic workflows), AgenticFlict |
| **Proactive scheduling and ownership partitioning** | Declared file and contract scopes are split into disjoint sets before execution, and merges are ordered along the producer-to-consumer graph, instead of detecting conflicts after they happen. | weak | NP-Bench / Nerveplane, Claude Code parallel-work surfaces (subagents, agent view, agent teams, dynamic workflows) |
| **Role-based SOP 'software company' teams** | Fixed human-like roles (PM, architect, engineer, QA) communicate through structured documents or chat, following a waterfall-like SOP. | weak | MetaGPT / MGX (MetaGPT X), ChatDev / ChatDev 2.0 (DevAll), SWE-Dev benchmark |
| **Multi-agent failure analysis and attribution** | Taxonomies and benchmarks that explain why multi-agent systems fail, which agent caused a failure, and when the multi-agent setup is worse than one agent. | strong | MAST: Why Do Multi-Agent LLM Systems Fail?, Who&When: automated failure attribution, Towards a Science of Scaling Agent Systems (Google), If Multi-Agent Debate is the Answer, What is the Question?, Rethinking the Bounds of LLM Reasoning: Are Multi-Agent Discussions the Key? |
| **Trained or native parallel orchestration** | The model itself is trained to spawn and coordinate parallel sub-agents, or the vendor exposes spawn/message/wait primitives in its API or CLI. | weak | Kimi K2.5 Agent Swarm, OpenAI Codex subagents / Responses multi-agent, Claude Code parallel-work surfaces (subagents, agent view, agent teams, dynamic workflows) |
| **Human-dispatched parallel sessions** | A developer runs several independent agents on separate tasks or worktrees and reviews the results. Coordination is human, and the bottleneck is review. | weak | Simon Willison: Embracing the parallel coding agent lifestyle, GitHub Agent HQ, Claude Code parallel-work surfaces (subagents, agent view, agent teams, dynamic workflows) |

## Open gaps

- No controlled study of multi-agent versus single agent on brownfield maintenance of a real, existing repo (the evidence is greenfield or oracle-rich: compilers, browsers, PaperBench, Commit0).
- No public cost-per-merged-change numbers comparing parallel swarms with a single agent once human review time is included.
- Automatic inference of file or contract ownership scopes for parallel agents is unsolved; current planners need hand-declared scopes.
- How to detect semantic (non-textual) integration breakage between agent branches beyond running the test suite.
- When a reviewer agent's findings are worth the extra loop (loop termination, false-positive cost); Cognition admits review loops can run long.
- Long-term code quality and maintainability of swarm-written codebases (the Cursor browser critique suggests poor architecture), not measured systematically.
- Failure taxonomies (MAST, Who&When) are built on 2024-era role frameworks; no taxonomy yet built from traces of modern coding swarms like Claude Code agent teams, Codex subagents or Gas Town.

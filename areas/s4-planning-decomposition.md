# S4. Planning & decomposition

Phase F1 broad sweep, 2026-11. Not yet verified in depth: `search-snippet` rows were not opened.

## State of the art

As of late 2026, planning for coding agents has settled on one main pattern: a durable, file-based plan (ExecPlan/PLANS.md, milestones with acceptance criteria and validation commands, a status/decision log) plus fresh-context workers per slice, with validation at milestone boundaries. Vendor systems (Cursor planners/workers/judge, Factory Missions, Devin manager/children, Codex 25h run) all converge on hierarchical planner->worker with a single writer per slice. Flat self-coordinating swarms with locks failed in practice. The strongest measured evidence says parallelism pays only when the work really decomposes: Google's 180-config study (+81% on parallelizable tasks, -39 to -70% on sequential ones) and Co-Coder (cohesion-aware graph partitioning beats file-per-agent and Claude Code Agent Teams on pass rate, cost and latency) both find naive parallel decomposition causes interface conflicts and error amplification. Several points are contested. One is whether explicit plan mode is still needed with frontier models: a Claude Code engineer said on HN that it is no longer useful, while many practitioners do more plan review, not less. Another is whether spec-heavy planning is waterfall. A third is how far METR time horizons can be used to size tasks; METR itself warns that the 50% horizon is not a safe delegation size and its error bars are about 2x. Plan quality matters a lot: a bad plan hurts more than no plan, and the planner-coder information gap explains most multi-agent codegen failures.

## Approaches

| Approach | What | Evidence | Seen in |
|---|---|---|---|
| **Living execution plan file (ExecPlan / PLANS.md / milestone plan + status log)** | A self-contained markdown plan the agent writes, updates and re-reads: milestones small enough for one loop, acceptance criteria and validation commands for each, a stop-and-fix rule, and a decision log to stop oscillation. Gives durable memory across context resets. | mixed | OpenAI Cookbook ExecPlans (PLANS.md), OpenAI: Run long horizon tasks with Codex (25h run), Anthropic: Building a C compiler with parallel Claudes |
| **Hierarchical planner -> fresh-context workers -> judge/validator** | Planners (possibly recursive) create tasks. Workers each take one task with a clean context and do not coordinate with each other. A judge or validation phase at cycle or milestone boundaries decides whether to continue or creates fix-up work. | mixed | Cursor: Scaling long-running autonomous coding, Factory Missions, Cognition: Multi-Agents: What's Actually Working, Gas Town (Yegge) |
| **Explicit dependency graph / ready queue (DAG task tracker)** | Tasks stored as a graph with blocking edges. Agents pull from the set of tasks whose blockers are all closed, ordered by critical path. Some trackers separate file-scope locks from real dependencies. | weak | Beads (bd), AR Labs: Task graphs for AI coding agents with Beads, Taskmaster (claude-task-master), Small DAG runners (taskflow, KAHN, graph-execution, swarmit, taskplane, OmoiOS) |
| **Cohesion/structure-aware partitioning for parallelism** | Decide what can run in parallel from static dependency structure (imports, symbol sharing) and the cost of passing context between agents, not one agent per file or feature. Isolate hub files and cluster tightly coupled code. | strong | Co-Coder: When Parallelism Pays Off, Towards a Science of Scaling Agent Systems (Google) |
| **Oracle-based decomposition of monolithic tasks** | When a goal is one giant pass/fail task, such as compiling the Linux kernel, use a known-good oracle to split it into independently failing sub-pieces so parallel agents stop colliding on the same bug. | weak | Anthropic: Building a C compiler with parallel Claudes |
| **Plan review gate (human or critic agent) before execution** | A read-only planning phase whose output is reviewed by a human (plan mode, plan annotation tools) or by a separate critic agent before any code is written. | mixed | Jules Planning Critic, HN: Plan mode is dead (Claude Code engineer comment and replies), Evaluating Plan Compliance in Autonomous Programming Agents |
| **Runtime-structured (code-controlled) decomposition** | The task graph and control flow live in executable code, not in a prompt. The LLM handles only focused judgment steps with schema-validated outputs, so only the failed subtask is retried. | weak | Runtime-Structured Task Decomposition (IBM), ADaPT: As-Needed Decomposition and Planning |
| **Vertical-slice / tracer-bullet issue splitting** | Split a PRD or plan into independently grabbable thin end-to-end slices, each a tracker issue that states its blockers. This is the human-practice root of many agent task graphs. | none | Matt Pocock to-issues / prd-to-issues skill, AR Labs: Task graphs for AI coding agents with Beads |
| **Capability-based task sizing (time horizons)** | Size delegated tasks by measured agent reliability against the length of the human task (METR 50%/80% horizons), while noting that the horizons are domain-specific and imprecise. | mixed | METR: Measuring AI Ability to Complete Long Tasks, METR: Clarifying limitations of time horizon, METR: Algorithmic vs Holistic Evaluation / Many SWE-bench-passing PRs would not be merged, On the estimation and validity of AI time horizons (Berkeley stats) |

## Open gaps

- No measured comparison of agent-written plan quality, such as dependency-edge accuracy, against human plans on real existing repos. AR Labs claims models infer dependencies worse than tasks but shows no data.
- No validated method for converting METR time horizons into a delegation size for low-context repo tasks. METR itself says the 50% horizon is not a safe size and the 80%/99% horizons are poorly identified.
- Little evidence on the best slice size for review cost (human minutes per merged slice) as opposed to agent success rate.
- No controlled study of whether an explicit plan-review gate still pays off with late-2026 frontier models. Evidence is anecdotal on both sides, apart from Jules' unexplained 9.5%.
- How a child agent's discovery should propagate to update sibling tasks and the plan (re-planning) is described as unsolved by Cognition and Cursor.
- Parallel decomposition results mostly come from greenfield or perfectly verifiable projects (compiler, browser, benchmarks). Evidence for brownfield work on employer repos is missing.

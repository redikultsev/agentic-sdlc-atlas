# S16. Release & change communication

Phase F1 broad sweep, 2026-11. Not yet verified in depth: `search-snippet` rows were not opened.

## State of the art

As of late 2026, release communication for agent-written code runs on a hybrid stack that is fairly settled. Deterministic tools (semantic-release, release-please, changesets, git-cliff, towncrier, GitHub release.yml) own version bumps and the raw list of what merged. An LLM owns only the prose: grouping changes by meaning, rewriting them for users, and filtering out noise. A human still edits or approves before anything is published. Every serious product (GitHub's copilot-release-notes, gh-aw release-notes, CodeRabbit Post-Merge Actions, Mintlify Autopilot, Linear Releases and agent-written project updates, Atlassian Rovo) ships drafts as a PR, an issue or a review queue, not as autonomous publishing. Research backs the quality claims only partly: ReleaseEval finds LLMs beat baselines when given commit-tree structure but struggle with raw diffs, and SmartNote (FSE 2025) wins on completeness and organisation. The open questions are trust and completeness, not fluency. The best-documented failure (Claude Code 2.1.198, July 2026) was an agent-heavy, daily-release product shipping a safety-relevant behaviour change with no changelog entry. Other open problems are hallucinated or prompt-injected entries in public notes, and a new machine audience: agents now read changelogs and SemVer labels, and smaller models check less when a release is labelled a patch. Closing the loop with the original requester after deploy is mostly vendor features (Linear customer requests, Productboard/Canny notifications, CodeRabbit MCP actions). I found no measured evidence on whether it works.

## Approaches

| Approach | What | Evidence | Seen in |
|---|---|---|---|
| **Deterministic structure, LLM prose, human edit (hybrid pipeline)** | Conventional commits, PR labels or fragments decide the version and the list of changes. An LLM only rewrites, groups and filters that list. A human edits the draft (Unreleased section, release PR, or issue) before it is published. | mixed | github/copilot-release-notes, Nazar Boyko: AI agents for release notes (honesty + injection critique), gh-aw release-notes workflow, Matt Palmer / Replit: 52 weekly changelogs with Claude Agent SDK, YugabyteDB AI-generated release notes |
| **Commit-convention-driven automated versioning** | semantic-release, release-please and git-cliff derive SemVer bumps and changelogs from Conventional Commits or squash-merged PR titles. With agents, the agent writes the PR title or commit message, often guided by a skill or AGENTS.md rule, and the release bot reads it. A mislabeled agent commit means a wrong bump. | mixed | semantic-release, release-please, git-cliff, Microsoft: Do AI coding agents care about SemVer? |
| **Fragment / changeset files written per PR** | Each PR carries a changeset or news fragment (changesets, towncrier, reno) that a person or agent writes at PR time. CI fails if one is missing. Some repos now tell agents in AGENTS.md how to write them. This moves the release-note judgment to merge time, when context is still fresh. | weak | changesets / AGENTS.md changeset rules (backstage, nocobase), towncrier / reno |
| **Post-merge follow-through agent** | After merge, an agent that already holds the PR context runs checked actions: updates CHANGELOG Unreleased, edits docs, opens follow-up tickets, posts Slack notifications. Applicability is decided before merge and is visible to reviewers. Output goes out as a follow-up PR or comment. | weak | CodeRabbit Post-Merge Actions, Mintlify Autopilot, PostHog scheduled agents (prod validation, docs drift) |
| **Tracker-native release and status communication** | The issue tracker owns release pipelines and stakeholder updates. An agent drafts release notes from the issues in a release, and project updates from issue changes plus Slack, for a human to refine and publish. | weak | Linear Releases + agent-assisted project updates, Atlassian Rovo Release Notes Drafter |
| **Close the loop with requester/customer** | Link customer requests or feedback to issues. When the issue ships, notify the requesters through a portal update, email or changelog entry, sometimes drafted by AI. | none | Linear customer requests, Productboard / Canny close-the-loop |
| **Machine-readable changelog for agent readers** | Treat the changelog as data: typed entries, stable IDs, one-line summaries, JSON/markdown/MCP endpoints. Downstream agents use it to decide upgrades, and SemVer labels change agent behaviour. | weak | ReleasePad: AI agents are reading your changelog, Microsoft: Do AI coding agents care about SemVer? |
| **Internal promotion / release intelligence** | An LLM summarizes what changed between environments for internal stakeholders, adding blast radius computed from the pipeline dependency graph. This is separate from user-facing notes. | weak | LLM-Augmented Release Intelligence (Bhati, arXiv 2603.14619) |
| **Release channels / staged trains for agent-speed shipping** | Stable, beta and canary channels, or batched trains, so that daily agent-produced changes do not reach every user at once. Practitioners propose this after silent-change incidents. I found little written about it specifically for agent output. | none | Claude Code 2.1.198 silent auto-continue incident (Olaf Alders) |

## Open gaps

- No measured data on completeness: how often agent-generated notes omit a user-visible change, as opposed to adding a false one. The Claude Code incident suggests omission is the costlier failure.
- No published system checks that every user-visible behaviour change has a changelog line, for example by diffing release artifacts or feature flags against notes.
- No measured evidence that closing the loop with the requester (customer or internal) works or how it should be done for agent-completed tasks; only vendor features.
- Release trains, channels or batching designed specifically for agent-speed output (daily releases) are discussed only in HN comments.
- No study of agents writing Conventional Commit types and the resulting rate of wrong SemVer bumps.
- No study of prompt-injection attacks on real release-note pipelines beyond GitHub's own hardening notes.
- Little on how a solo developer should split communication between employer repos (internal promotion notes) and personal or public repos.

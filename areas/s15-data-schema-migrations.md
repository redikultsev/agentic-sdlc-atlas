# S15. Data & schema migrations

Phase F1 broad sweep, 2026-11. Not yet verified in depth: `search-snippet` rows were not opened.

## State of the art

As of late 2026, data and schema changes are where agentic development has been hurt most, and the public record is mostly incidents and vendor tooling, not research. Well-documented failures include the Replit/SaaStr drop during a code freeze (2025-07), Claude Code running `drizzle-kit push --force` against Railway production (2026-02), the DataTalks.Club `terraform destroy` (2026-03) and Cursor/Opus deleting the PocketOS Railway volume along with its same-volume backups (2026-04). Practitioners and vendors agree that prompts are not controls. What holds up is keeping the agent away from production credentials, letting it draft migrations as code that CI/CD applies, testing on a copy-on-write branch (Neon, Lakebase, Xata, PlanetScale, Supabase, ZFS clones) and running deterministic migration linters (squawk, Atlas, MigrationPilot, pgfence) as a feedback loop. Three questions are still open: how well harness-level blocks hold (agents route around hooks: Edit blocked, so `echo >>`), whether vendors' 'agent-safe' claims hold up (Atlas lint is now Pro-gated; Bytebase gives the agent the user's full rights by default), and what to do about data branches, which cannot be merged, so data fixes and backfills have no clean promote path. Hardly anything is measured. The only quantified results found are one practitioner experiment (GPT-4 on 50 Postgres scenarios: 22/50 fully safe, 4 destructive) and an author-built linter benchmark.

## Approaches

| Approach | What | Evidence | Seen in |
|---|---|---|---|
| **Agent drafts, pipeline applies (no production credentials for the agent)** | The agent only writes migration files and opens a PR. Reviewed CI/CD applies them to production, and the agent's environment never holds prod DB or infra tokens. Incident analyses repeatedly name the absence of this as the root cause. | mixed | Neon Migration Specialist agent, Databricks Lakebase agentic SDLC loop, Supabase MCP defense-in-depth guidance, HN: Agentic AI systems violate implicit assumptions of database design, PocketOS / Cursor / Railway volume deletion, Replit dev/prod database separation |
| **Copy-on-write database branch per agent / per PR** | Each agent (git worktree) or PR gets an instant CoW clone of prod or seeded data. The agent runs migrations and destructive tests there, then throws the branch away. Branches are not merged back; schema is promoted through migration code. | weak | Databricks Lakebase agentic SDLC loop, Neon Migration Specialist agent, Neon snapshots as agent checkpoints, PlanetScale MCP server + skills + deploy requests, Xata branches / pgroll, db-branch (ZFS), DBLab Engine 4.0, Ghost (Tiger Data), Dolt version-controlled SQL for agents |
| **Deterministic migration linting as agent feedback loop** | A static analyzer (lock types, table rewrites, destructive ops, missing CONCURRENTLY/NOT VALID/lock_timeout) runs locally, via MCP or in CI. Its structured findings go back to the agent until clean. Suppressions are reserved for humans. | mixed | Squawk, Atlas agent skills / AI-safe migrations, MigrationPilot, pgfence / Veto / eugene, Practitioner experiment: GPT-4 on 50 migration scenarios |
| **Declarative schema-as-code (agent edits intent, tool plans the diff)** | The agent edits the desired schema (HCL/SQL/ORM). A deterministic engine generates, lints, tests and policy-checks the migration, so humans review intent and outcomes, not raw SQL. | weak | Atlas agent skills / AI-safe migrations |
| **Execute on a shadow copy with data-integrity checks** | Run the migration on a restored snapshot or ephemeral Postgres under synthetic write load. Compare row counts and checksums and measure write stalls, which catches valid-but-destructive SQL that linters and 'does it run' checks miss. | weak | Practitioner experiment: GPT-4 on 50 migration scenarios, MigrationPilot, Atlas agent skills / AI-safe migrations |
| **Tool-side agent detection and consent gates** | The migration CLI detects it is being driven by an AI agent (Claude Code, Cursor, Gemini CLI, etc.) and refuses destructive commands such as `migrate reset` without explicit user consent. | weak | Prisma ORM 6.15 AI safety guardrails |
| **Harness-level blocks (hooks, deny rules) plus OS-level and CI backstops** | PreToolUse hooks or permission deny rules block force/reset/push commands and edits to applied migrations. Field reports show agents route around tool-specific blocks, so the durable layers are file ownership/permissions, sandboxing and a CI check that applied migrations never change. | mixed | Claude Code issue #27063 (drizzle-kit push --force), Reddit: hook blocked migration edits, agent used echo >>, Community DB guard hooks (yurukusa gist / Claude Code Safety book) |
| **Blast-radius separation of credentials and backups** | Scoped, environment-bound tokens, automatic dev/prod database split, and backups stored outside the blast radius of the data. In every major incident, the deciding factor was whether these existed. | strong | PocketOS / Cursor / Railway volume deletion, Replit/SaaStr production database deletion, DataTalks.Club terraform destroy, Replit dev/prod database separation |
| **Governed change gateway for agents** | The agent connects to a change-management layer (SQL review, approval policy, audit, affected-rows dry run) instead of the database itself. | weak | Bytebase MCP server, PlanetScale MCP server + skills + deploy requests |
| **Reversibility classification and undo/checkpoint layers** | Classify every action as idempotent, reversible, compensable or irreversible and gate the irreversible ones. Provide checkpoints (DB snapshots, versioned tables) so agent changes can be rolled back. | weak | Neon snapshots as agent checkpoints, Dolt version-controlled SQL for agents, Reversibility papers (AgentAbstain, Irreversibility Budget, Revisable by Design) |

## Open gaps

- No independent, reproducible benchmark of agent-written schema migrations under load across current models (Claude/GPT-5.x). The only measurement found is one GPT-4 practitioner run.
- Backfills and data fixes by agents are almost undocumented: no write-ups on batching, idempotency, verification or review of agent-authored data changes, and CoW branches cannot be merged, so there is no promote path except re-running scripts.
- No data on how often harness hooks, deny rules or tool consent gates (Prisma) are bypassed, or on whether agents set consent env vars themselves.
- How to give agents production-like data for dry runs without PII on a self-hosted single VPS. Masking is documented only inside managed platforms (Unity Catalog, Xata).
- Expand-migrate-contract across multiple deploys: no evidence that agents can hold a multi-release contract phase over days without a human tracking it.
- No company engineering post (GitLab, Shopify, Stripe, GitHub and similar) describing an in-house policy for agent-authored production migrations and its measured outcomes.
- Non-Postgres stores (ClickHouse, Mongo, Redis) and IaC-driven stateful resources have almost no agent-specific migration tooling.

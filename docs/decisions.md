# Pipeline design decisions

What was decided and why. A new decision is a new row; a changed one is edited in place with the revision date; a cancelled one is marked "cancelled" with the reason, never deleted.

Basis: research on how leading teams build agentic pipelines (`research/atlas/research/2026-11-how-leaders-build-pipelines.json`): nine stages that Stripe, Anthropic, Spotify, Google, Cognition, AWS AI-DLC and others converge on, and an artifact chain named after the CDEvents standard.

| # | Question | Decision | Rejected | Why | Date |
|---|---|---|---|---|---|
| 1 | Where the main human gates sit | On the spec and plan, before code. Merge by risk class | Every PR (Stripe, Spotify, GitHub); merge with no human (OpenAI, Cognition) | A wrong idea is cheaper to catch before code (HumanLayer, Factory, AWS AI-DLC). Operator attention is the scarcest resource | 2026-11-20 |
| 2 | How heavy the spec is | By work item size. The agent always reads the code and plans; size decides what is written down and what the Operator approves. S: straight to code; M: spec and plan; L: plus a codebase research document | Always full; always light | AWS and HumanLayer moved to adaptive depth themselves; heavy specs are slower than code on small tasks (Thoughtworks) | 2026-11-20 |
| 3 | What to look at before merge | Evidence: check output, screenshots, video. Code only for risky changes | Always the code (Osmani, Willison) | How Cognition and Cursor work | 2026-11-20 |
| 4 | Where the pipeline hub is | The tracker: spec, agent sessions and PRs link to the work item number | Chat and sessions; files in the repo | With many parallel agents you can see what is in progress and what is stuck | 2026-11-20 |
| 5 | Tracker | Any tracker, connected as an MCP server (GitHub Issues, Jira, others); the engine needs no built-in support for a particular tracker | GitHub Issues only; Linear; a custom one; an adapter per tracker in the engine | Different projects use different trackers; MCP servers already exist for each (revised 2026-11-21) | 2026-11-20 |
| 6 | How to merge by risk | R0 merges itself on green checks and AI review; R1 the Operator merges on evidence; R2 the Operator reads the code. Revised 2026-11-20: R0 is decided by the auto-merge rules file at merge, not by the agent (decision 25) | Everything through the Operator, auto-merge later | Anthropic and Intercom do this (19% of PRs with no human) | 2026-11-20 |
| 7 | Who sets size and risk | The agent proposes with a reason; the Operator corrects when accepting the work item | The Operator alone; the agent alone | One action, but an agent underestimate does not slip through | 2026-11-20 |
| 8 | When a change goes to production | Every merge deploys main right away, R0, R1 and R2 alike; R2 is approved at the Merge gate, where "merge" means "deploy now". Revised 2026-11-20 (decision 26) | Every deployment on a yes; a separate "Deploy R2?" gate after merge | A gate after merge does not hold when main deploys itself: the next R0 deploy would ship the waiting R2. No researched team uses that shape (`research/atlas/research/2026-11-deploy-and-watch.md`) | 2026-11-20 |
| 9 | How many work items in parallel | At most N (start with 3) wait for the Operator at once; beyond that new ones do not start | A hard agent limit; no limit | The bottleneck is attention: one person actively supervises 2–4 agents (atlas X10) | 2026-11-20 |
| 10 | Which repositories first | Personal and work ones at once. Revised 2026-11-21: the engine's files (specs, plans, ADRs, auto-merge rules, agent instructions) live in each repository, work ones included | One first, then expand | One storage everywhere: the rules and the specs sit next to the code they describe; an earlier consequence (no engine files in work repositories) contradicted decisions 14 and 25 | 2026-11-20 |
| 11 | How the pipeline talks to the Operator | By universal presentation rules: decision type sets the depth, a real before/after case is mandatory, "not verified" on top, form chosen by the task. Recommendation first for small decisions, after the facts for big ones | Card templates for 7 decision types; a one-line question | Research on presenting decisions (`research/atlas/research/2026-11-decision-presentation.json`) | 2026-11-20 |
| 12 | Where the Operator works with the pipeline | Claude Desktop for now | — | The engine is not chosen yet | 2026-11-20 |
| 13 | Language | Everything in the project in English: model, docs, deck, research | Russian | The material is shown to colleagues | 2026-11-20 |
| 14 | Specs and decisions store | Holds per work item spec, plan and research, and per project decision records (ADR). Interviewer and Planner read past decisions; Implementer reads the plan; AI review reads the spec | A separate ADR store; no decision log (rules in AGENTS.md only) | One store keeps the overview simple; without ADRs the "why" behind old choices is lost | 2026-11-20 |
| 15 | Fix rounds before Blocked | At most 3 rounds of fix after red checks, then the work item is Blocked and waits for the Operator | 2 rounds | Matches the work item states; a common cap in the researched pipelines | 2026-11-20 |
| 16 | Several agents on one work item | One fresh Implementer session per slice. Each slice is a sub-issue of the work item with "blocked by" links; the Orchestrator works the frontier (slices whose blockers are done) and runs frontier slices with no shared files in parallel, each in its own sandbox. It merges slice branches; a conflict goes back to the Implementer. Revised 2026-11-20: slices moved from the plan document to tracker sub-issues; a sandbox per parallel slice instead of a worktree (Stripe, Ramp: worktrees do not scale) | Sequential only; slices only inside the plan document; a free-form team of agents | Faster on big work items; dependencies are explicit and visible in the tracker, so code, not an agent, decides what runs in parallel. Parallel agents on shared code make clashing decisions (Cognition). Slices as tickets with blocking edges: Pocock's to-tickets | 2026-11-20 |
| 17 | What Triage does before sizing | Works it out alone from the request, alerts, logs and code; never asks people. Checks duplicates, that the behaviour is not already built, and the register of rejected requests; reproduces a bug; writes down assumptions where something stays unclear. Proposes an outcome: for the agent, for a human, won't do. The Operator decides at Accept. Revised 2026-11-20: "needs info" (questions to the requester) removed by decision 19 | Accept or cancel only; questions to the requester (Pocock's needs-info) | Saves agent runs on work that exists or was rejected; not every item suits an agent. Pocock's triage skill, minus the questions | 2026-11-20 |
| 19 | Who resolves ambiguity | Agents resolve it themselves from the sources they can read (request, alerts, logs, code, past decisions), write down their assumptions and go on. People are reached only at the gates, where the Operator sees the assumptions and can correct them. One exception: the Interviewer in Spec asks the Operator about business choices, few and short, by the presentation rules (format still open) | Agents ask the requester or the Operator questions mid-stage | The Operator's attention is the bottleneck of the whole pipeline; a written assumption checked at a gate costs less than a wait for an answer | 2026-11-20 |
| 20 | Who writes code and tests, and how they stay honest | One agent, the Implementer, is the only one that changes code: per slice it writes unit tests first, then code, in its own sandbox. What "done" means lives in one place: the acceptance criteria of the spec, each with 2–3 key examples. After CI (outside the sandbox) a separate Validator with a fresh context and its own sandbox checks those criteria on the running app, records evidence for the PR and never edits code. Revised 2026-11-20: no separate scenarios (first hidden, then visible); Evidence merged into the Validator | A separate test-writer agent; hidden scenarios in their own store (StrongDM); visible scenarios written by a Scenario writer next to the spec; the Implementer checking itself | One writer and an independent checker is the production pattern (Stripe, Spotify, Factory, Cognition, Anthropic). Concrete examples are what helps agents (+8–46 points at function level); a second scenario document duplicates the criteria, drifts and doubles review (Böckeler, Adzic, Marcano). Research: research/atlas/research/2026-11-roles-tests-sandboxes.md, research/atlas/research/2026-11-criteria-vs-scenarios.md | 2026-11-20 |
| 21 | Sandbox rules | A disposable sandbox per agent session; everything that changes or runs code runs inside. Network closed by default; push only through a proxy to one branch; no merge rights; the authoritative CI runs outside | A sandbox per work item shared by parallel slices; credentials inside the sandbox | The common pattern of Codex, Copilot, Claude Code on the web, Stripe and Spotify | 2026-11-20 |
| 22 | How AI review is built | One AI reviewer agent: fresh context, own sandbox, a different model family than the Implementer. It reads the PR, spec and surrounding code, re-checks each finding (by running the code where it can), skips style and nits by a "what not to flag" list, gives a JSON verdict and for R1/R2 explains the change to the Operator. All fix rounds share one limit of 3; a block verdict or the limit sends the work item to Blocked | Reviewers + judge + change explainer (3 agents); parallel specialists with a judge (Qodo, Uber, Cloudflare) | The biggest measured gains came from one agentic reviewer with tools (Cursor Bugbot 52% → 70%+, Greptile v3) and from dropping comment categories (Uber, Google, Cloudflare, Datadog); a separate fact-check judge added almost nothing at Atlassian. A separate verifier can be added if measured noise is high. Research: research/atlas/research/2026-11-ai-code-review-shape.md | 2026-11-20 |
| 23 | Order of checks after the code | CI → AI reviewer (white-box, stage 5 "Checks & review") → Validator (black-box, stage 6 "Acceptance"). The Validator does not see the reviewer's verdict. After any fix, the reviewer reviews only the new diff and the Validator re-checks the criteria the fix touched | Validator before the reviewer; both in parallel; one agent doing both | Cheap and deterministic first, expensive last: review $1–25 and 1.5–20 min, black-box validation $3–30 and 5–11 min per pass and flakier (Anthropic, Slack). Review findings change code and would invalidate an earlier validation. Factory, Devin, Spotify and classic pipelines (Google, Fowler/Humble) order it this way. A judge shown a prior verdict anchors on it (CIKM'26). Research: research/atlas/research/2026-11-review-vs-validation-order.md | 2026-11-20 |
| 24 | How a PR lands | Through a merge queue: the PR is rebuilt on the latest main with the PRs ahead and the full CI runs again; approvals stay valid while the PR's own diff is unchanged; a red build or a conflict ejects it to the Implementer, and after a conflict fix the changed part goes through checks, review and acceptance again. At the gate the Operator sees the scope first (files outside the plan, new dependencies, size), then the explanation and evidence, for R2 the code; "changes" with a comment goes back to the Implementer and does not count toward the 3 automatic rounds | A merge script that only checks the PR head; re-reviewing on every main change | Every merge queue (GitHub, GitLab, Uber, Shopify) re-runs full CI on the latest main and keeps approvals while the diff is unchanged; 27.7% of open agent PRs have conflicts; reverts of agent PRs come mostly from scope overreach (22.3%). Research: research/atlas/research/2026-11-merge.md | 2026-11-20 |
| 25 | When a change merges without the Operator (R0) | Only when a rules file in the repo matches all facts: allowed paths and change types (docs, tests, dev tools, patch updates), size limit, no new dependencies, never-zones untouched (migrations, auth, payments, CI config), all checks green, working hours. Kill switch: a change type whose merged changes are reverted more than 5% over 30 days loses auto-merge until the rules change. The agent's R0 is only a forecast | The agent decides R0; every change through the Operator until there is history | Everyone who auto-merges does it by mechanical rules per change type with monitoring and a kill switch (Spotify Fleetshift 77% automerged, Meta RADAR, Renovate); free-form agent PRs without a human only at OpenAI in one repo. Research: research/atlas/research/2026-11-merge.md | 2026-11-20 |
| 26 | How a deploy is watched and rolled back | Deploy goes to all users at once; every merge deploys as soon as it lands, deploys never run in parallel and do not wait for a watch window. The Watcher agent watches each deploy for a window (30 min by default): first what the PR changed (errors from the changed code, the business numbers it touches), then the whole service. On a clear regression it rolls back by itself, then reports to the Operator and sends a work item with evidence to Triage; when unsure it asks. More than 2 unneeded rollbacks in 30 days: it asks before rolling back. Migrations ship expand–contract and are never rolled back automatically. Revised 2026-11-21: one Watcher per deploy, windows overlap. A regression pinned on one PR is rolled back by reverting that PR (the revert deploys at once, no gate); when it cannot be pinned on one PR, back to the last version before all open windows | Staged rollout (canary); a script with fixed thresholds instead of the agent; asking the Operator before every rollback | The Operator's choice: one universal agent instead of a per-service script, and it knows what the PR changed, so it sees a regression in one flow that a service-wide threshold misses. Researched teams roll back automatically and ask a human only when unsure. Risk: no staged rollout and no canary, so a bad change reaches everyone for the minutes until the rollback, and before/after comparison is noisier than canary vs stable (Google SRE) | 2026-11-20 |
| 27 | How the pipeline learns | A weekly Retro agent reads corrections and failures (Operator changes and edits, Blocked items, fix rounds, reviewer findings, Validator failures, rollbacks, traces); what repeated twice becomes a work item for Triage with the cases and the file to change. A rule that must hold becomes a check with a fix hint; guidance becomes an instruction line; guidance broken again becomes a check. Rules unused for 8 weeks are proposed for removal; root instructions ≤150 lines. Instruction and rules files never R0; weakening a check is R2. Weekly summary of six metrics to the Operator; revised 2026-11-22: seven, the seventh is how often the Operator chose the recommended option (decision 38) | A separate "Adopt rule?" gate; learning only from session traces; rules only as prose | No researched team has a separate adopt gate: the PR is the approval (OpenAI). Corrections are the signal everyone uses. Prose rules are followed less as they grow (IFScale), mechanical checks always hold (OpenAI, Anthropic, Factory). Weakening a check is how an agent games a metric (METR). Weekly cadence and the pushed summary are our choice, no precedent (`research/atlas/research/2026-11-learn.md`) | 2026-11-20 |
| 28 | Work item states | 15 states named by who holds the item: agent states end in -ing (Triaging, Specifying, Planning, Implementing, Verifying, Live), Operator states end in Review (TriageReview, SpecReview, PlanReview, MergeReview) plus Blocked; closed: Done, RolledBack, ForHuman, Cancelled. No states that last seconds (accepted, merged are transitions); Researching is part of Planning. The Operator can cancel in any state; closing tells the requester why. Shown as a UML state machine in swimlanes Operator · Agents · Closed | 18 states incl. Accepted, Researching, Merged; states named by the result (New, Triaged) | A state must say who has the ball, or the board does not show where the Operator is the bottleneck; UML state machine guidelines (Ambler). `docs/states.md` | 2026-11-21 |
| 29 | Limits on an agent session | Every agent session has a time and a cost limit, set in config; first values come from the first measured work items. The Orchestrator stops a session that hits a limit, and it counts as a failed fix round | No per-session limit, only the 3 rounds | Without a limit a stuck session burns time and money without counting toward Blocked; the 3-round limit only counts finished rounds | 2026-11-21 |
| 30 | Pausing the pipeline | The Operator can pause the whole pipeline: no new agent sessions start, running ones finish to their next state; resume starts them again | Only the R0 auto-merge kill switch (25) | During an incident the Operator needs agents to stop shipping new changes without killing work in progress | 2026-11-21 |
| 31 | Problems noticed outside the task (discoveries) | Any agent that notices a problem outside its own task (Implementer outside its slice, AI reviewer and Validator outside the change, Planner outside the work item) never fixes it in place: it records a discovery with its evidence (where, what, how it was seen), and the discovery goes to Triage as a new signal. Triage handles it like any other: duplicates, already built, the register of rejected requests (which also keeps a rejected discovery from being raised again), reproduction; the Operator accepts it at TriageReview as usual. The current work item does not wait for it | Fix it in the same PR; drop it; a separate drain agent that files, tracks or drops on its own (Archon's SDLC pack); weekly batches for the Operator | Scope overreach is the top cause of reverted agent PRs (22.3%, `research/atlas/research/2026-11-merge.md`); dropping loses real defects. Triage already does what Archon's drain does, and the rejected register fixes the drain's flaw: Archon remembers a drop per run only, so the same defect is judged again (`research/atlas/research/2026-11-archon-pipelines-vs-ours.md`). Risk: discoveries count toward the limit of 3 items waiting for the Operator (decision 9) | 2026-11-22 |
| 32 | Where the Operator's answers live | Every Operator answer (a gate comment, an answer to the Interviewer, sorting out a Blocked item, a merge "changes" comment) is a ruling. The Orchestrator appends it, dated and in the Operator's words, to a "Rulings" section of the work item's spec (for S, of the work item itself); later sessions of that item work from it, and a comment that contradicts it is a question, not an order. The decision request lets the Operator mark an answer as true for the whole project; such a ruling also goes to the project's register of rulings, which every agent reads before it asks the Operator or raises a finding | Answers only in the chat or the PR thread; only in the spec; only through the Retro's weekly rules | A fresh session does not see an answer it was not given, so it asks again or undoes it; the Operator's attention is the bottleneck (decision 9). Archon writes a ruling into the issue body as a dated "Current scope" section and keeps a rulings file read before any agent asks (`research/atlas/research/2026-11-archon-pipelines-vs-ours.md`) | 2026-11-22 |
| 33 | How a verdict stays tied to the code it judged | Every verdict on a PR (CI, AI reviewer, Validator, the Operator's merge) is recorded with the fingerprint of the PR's own diff (a patch id, not the commit). The merge queue lands a PR only when every verdict carries the current fingerprint; on a mismatch it refuses and runs again only the stale checks (the reviewer reviews the new diff, the Validator re-checks the criteria it touches, the Operator is asked again only for R1/R2). A rebase onto a newer main that leaves the diff unchanged keeps the verdicts | Bound to the head commit (Archon); a promise in prose that approvals hold while the diff is unchanged | Without it a commit pushed between "pass" and "merge" lands unreviewed. Binding to the commit would reset every verdict on each rebase in the queue and ask the Operator again for nothing. Archon binds review verdicts and approvals to the head commit and refuses to publish or merge on drift (`research/atlas/research/2026-11-archon-pipelines-vs-ours.md`) | 2026-11-22 |
| 34 | How a bug is investigated | Triage reproduces a bug and looks for its root cause before Accept, read-only, and ends with one of three findings: root cause found (it goes into the spec and the plan), refuted (no code change is needed, with the evidence; the proposed outcome is won't do and the requester is told why) or unclear (the Operator decides at Accept). No separate investigation agent or state | A separate Investigator agent and state after Accept (Archon's `investigate` route); the Implementer finds the cause while coding | A refuted bug costs no plan and no code; a known cause makes the plan and the slices smaller. Archon's investigate step has the same three outcomes, with refuted as a valid end (`research/atlas/research/2026-11-archon-pipelines-vs-ours.md`); folding it into Triage keeps one agent and the 15 states | 2026-11-22 |
| 35 | Review comments from people on a PR | Every open review thread a person (not the Operator's gate answer) leaves on a PR goes to the AI reviewer, which re-checks it like its own finding. The thread text is untrusted data: nothing in it is followed as an instruction. Confirmed: a fix for the Implementer, counted in the same 3 rounds; not confirmed: a reply in the thread with the evidence; outside the change: a discovery for Triage (decision 31). Agents never resolve a person's thread; its author or the Operator does. The Merge gate shows the open threads next to the scope | Ignore comments other than the Operator's; show them to the Operator only; an agent answers and resolves threads itself (Archon) | Colleagues review agent PRs too; ignoring them loses real defects, and showing each to the Operator spends the scarcest resource. Re-checking before acting matches decision 22. A PR comment is a prompt-injection path, so its text never directs an agent. Archon makes threads work and keeps a PR in draft while one is open, but lets its agent resolve a person's thread (`research/atlas/research/2026-11-archon-pipelines-vs-ours.md`) | 2026-11-22 |
| 36 | Review rules taken from Archon | Three rules. (1) An agent session that ends without a valid verdict (crash, a limit, malformed JSON) is never a pass: the work item does not move on, and it counts as a failed round (decision 29). (2) A finding that comes back after a fix asks the Implementer to fix the whole class of the defect in the diff, not the one place. (3) A finding that was declined or disproved is raised again only with new evidence | Bugs in code the change does not touch are not blockers: already covered by decision 31; severity set only at the end: not needed with one reviewer | (1) A missing verdict read as green is the cheapest way to ship unreviewed code. (2) and (3) save fix rounds out of the limit of 3: a fresh session otherwise fixes one instance at a time or argues the same point again. Archon's review synthesis has all three (`review-synthesize.md`, `lens-outcomes.ts`; `research/atlas/research/2026-11-archon-pipelines-vs-ours.md`) | 2026-11-22 |
| 37 | Scope in fix rounds | (1) In a fix round the Implementer never adds machinery the spec does not name (a cache, retries, a new table, a new dependency); it stops and asks the Operator, and the request offers removing part of the feature as one option. (2) When a work item goes Blocked after 3 rounds, the request to the Operator says whether the defects shrank round by round or were new each time, with a recommendation (one more round, or back to the plan). The limit of 3 stays hard | Only cosmetic changes never earn a round: left out, the "what not to flag" list covers it; Archon's judgment at the cap instead of a hard limit | Fix rounds grow the change; scope overreach is the top cause of reverted agent PRs (`research/atlas/research/2026-11-merge.md`). The Operator decides a Blocked item faster with the trend in front of them. Archon's build queue asks with the subtractive option and judges convergence at its round limit (`answer.md`; `research/atlas/research/2026-11-archon-pipelines-vs-ours.md`) | 2026-11-22 |
| 38 | Shape of a decision request | Every option carries the exact action the Orchestrator takes when the Operator picks it, so code acts on the choice and no agent interprets the answer; an "other" option with free text is always there. The request names a recommended option, why, and the agent's confidence. Code rejects a malformed request (a recommendation that matches no option, repeated options) before it reaches the Operator. The Retro reports how often the Operator chose the recommendation, per type of request: near-always means a candidate for automation, often not means the agent judges badly there | Free-text answers read by an agent; a recommendation without confidence | Reading the Operator's answer as prose is where an agent can act on the wrong option. The follow rate is the measure for moving a decision from the Operator to the pipeline. Archon's attention items carry an effect per option, a recommendation with confidence and an automatic "other", and are validated before they are raised; its constitution proposes counting answers that followed the recommendation (`research/atlas/research/2026-11-archon-pipelines-vs-ours.md`) | 2026-11-22 |
| 18 | How to check the model for gaps | After the deck walkthrough, every stage answers five questions: what triggers it, what it reads and writes, what it triggers next, where a human re-enters, what stops two runs doing the same work | Review by eye only | A finished design answers all five for every task (Pocock's software-factory) | 2026-11-20 |
